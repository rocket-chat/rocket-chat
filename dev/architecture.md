# Architecture

How Rocket Chat is built, how a request becomes a finished turn, and where each responsibility lives. Rules for working in the code are in [`AGENTS.md`](../AGENTS.md); identity, isolation and secrets are in [`security-and-tenancy.md`](security-and-tenancy.md). End-user and operator documentation is the site in `doc/`.

## 1. Shape of the system

One control-plane process, one database, and sandboxes that are created on demand.

```
 Web cockpit (Next.js 15)      Slack (Socket Mode)      GitHub webhooks      Scheduled missions
        |  REST + WebSocket          | (in-process)           | HTTP               | (in-process)
        v                            v                        v                    v
 +--------------------------------------------------------------------------------------------+
 |  Control plane  (apps/api, FastAPI, one process per replica)                               |
 |  routers -> turn engine -> orchestrator (agent-core) -> tools                              |
 |                  |              |                          |                               |
 |            event bus       LLM gateway              sandbox driver (Docker | Kubernetes)   |
 |                  |         (LiteLLM, BYOK, budgets)        |                               |
 +------------------|---------------------------------------|-------------------------------+
                    v                                       v
          PostgreSQL 16 + pgvector                 One sandbox per session
          (row-level security, LISTEN/NOTIFY)      (container or pod + persistent workspace)
```

Design choices that shape everything else:

* **No worker tier.** A turn is a coroutine in the API process. Slack, the mission scheduler, the sandbox reaper, retention and turn-lease heartbeats are `asyncio` tasks in the same process (`api/bootstrap/`). Several replicas cooperate through PostgreSQL only: a shared event bus (`LISTEN`/`NOTIFY`), advisory locks for "one turn per session" and leader election, and claim-based work queues.
* **Contracts first.** Every subsystem is used through a protocol in `specifications/interfaces/` (sandbox driver, LLM gateway, session store, event bus, transcript store, git engine, plus the typed event payloads). `packages/` never import from `apps/`; `specifications` imports no workspace package (enforced by `tests/unit/test_import_boundaries.py`).
* **Sessions start blank.** A session is a sandbox with an empty `/workspace`. The agent finds and clones repositories itself (`clone_repository`); nothing is pre-cloned by the platform.
* **PostgreSQL is the only state.** Sessions, turn traces, transcripts, memory, audit, usage, settings, missions, processes and the sandbox catalogue are tables. With no `DATABASE_URL` (tests, a laptop) the same protocols are served by in-memory stores.

## 3. The agent (`packages/agent-core`)

**Orchestrator.** `AsyncReActOrchestrator` runs the reason-and-act loop. A turn is a `_TurnRun` driven through phase methods: `_begin_turn_run` → `_drive_turn` → `_react_step` (stream one model response, dispatch its tool calls, append results) → `_synthesize_after_budget` / `_fail_turn`. When the turn budget is spent while the model is still calling tools, one last tool-less step synthesises an answer from what was gathered (`post_failure_synthesis`), so findings are never left half-finished. `human_wait_scope` lets the process-wide concurrency gate release its slot while a turn waits for a person.

**Engine notes.** What the engine tells the model during a turn (budget notice, stale or unfinished checklist, "you wrote a tool call as text", the final-synthesis instructions) lives on the `_TurnRun` (`sticky_notes` for the rest of the turn, `next_notes` for the next request) and is rendered by `notes.py` at the end of the request as one user-role `<system-reminder>` block, merged into the last user message when the request ends with one (unless that message carries the cache breakpoint). Notes are never stored. A request's only `system` message is the leading stable prompt: LiteLLM's translation for several provider families moves every system message into the system prompt, so a stored mid-history notice would become a standing instruction. The gateway logs a warning if one slips through, and rehydration drops the system messages older transcripts stored.

**Request layout and prompt caching.** Every request is: the session-stable system prompt (the only `system` message, cacheable) → the conversation → one trailing user-role `<system-reminder>` holding the turn's volatile context (`SystemPrompt.dynamic`: routing notice, background processes, GitHub activity; recalled memories) and the engine notes. A provider caches up to the first byte that differs, so nothing that changes between turns sits before the history. The last conversation message of each request carries a rolling cache breakpoint (`with_cache_breakpoint`), so each step reads what the previous one wrote; with the stable prompt and the tools that is three of the four explicit markers Anthropic-style providers allow, and providers with automatic prefix caching ignore the flag. Tool schemas are ordered stably (`get_tool_definitions`). The turn trace records `usage.cache_hit_ratio`.

**Reasoning.** A step's reasoning text and, for providers that sign it, its reasoning blocks are kept on the assistant message that carries the step's tool calls (with any text the model wrote before calling). The gateway sends them back as each family requires (`reasoning_replay`): Anthropic-style extended thinking gets its signed `thinking_blocks` (and no `temperature`), DeepSeek gets `reasoning_content` within the current tool loop, other families nothing; Gemini's thought signatures already travel in LiteLLM's tool-call ids, which are kept as given.

**Execution context.** `current_execution_ctx` (a `contextvar`) carries the session, organization, user, event queue, permission mode, sandbox capabilities and per-turn callbacks. Tools and subagents read it; nothing mutates shared singletons across turns (`tests/unit/test_no_shared_turn_state.py`).

**Tools.** `ToolRegistry` (FastMCP-based) holds Tier 1 tools (in-process: web, knowledge base, GitHub reads, memory, planning, questions, delegation) and Tier 2 tools (run in the sandbox through the driver: files, search, shell, tests/lint/build, git, package manager, background processes, browser, image viewing). Built-in tools are registered in groups from `tools/builtin/<domain>.py`; their implementations are sibling modules. The registry is also the enforcement point:

* **Permission modes** (`permissions.py`, modes `plan`, `ask`, `auto_edit`, `auto` (default), `bypass`): every tool call is classified as read, edit, command or publish with a risk level, and the session's mode decides which classes raise a human gate *before* the tool runs (`ask` gates edits and commands, `auto_edit` gates commands and publishing). `plan` rejects every mutating tool server-side, whatever the model says.
* **GitHub tools** (`builtin/github.py`, `builtin/repository.py`; HTTP in `github_client.py`, pull requests in `github_prs.py`, Actions/releases/search in `github_ci.py`, `github_api` in `github_generic.py`) run on the platform: the sandbox holds no GitHub credential and its `gh` is a stub. Reads use `TurnCallbacks.github_access` (the session's read credential). Changes use `TurnCallbacks.github_write_access(repository)`, which `api/turns/callbacks.py` resolves per repository: the member under `pr_creation: as_user`, else the App installation mapped to the organization (`inherit_permissions`, not lowered to read), else the member. The `GithubAccess.actor` it returns is shown in each result. These tools carry an `action` argument, so they are classified per call (`ACTION_CLASSIFIED_TOOLS`): read actions are reads, changes are publishes, and `merge` and `github_api` `DELETE` are critical (gated in every mode but `bypass`). `github_generic.py` holds the endpoint and mutation deny lists.
* **Sandbox types and workspace release:** a catalogue entry may name a placement profile (`sandbox_driver/profiles.py`, defined only by the operator in `K8S_SANDBOX_PROFILES`; the Kubernetes driver applies node selector, tolerations, runtime and priority class, labels, annotations, storage class and sizing, the Docker driver ignores it) and override CPU, memory and disk (precedence: agent > type > organization). `services/workspace_release.py` runs hourly on the schema-owner connection: a session whose sandbox is not running and whose record has not changed for its delay (`sandboxes.workspace_release_days` or the type's `release_after_days`) has its workspace destroyed through the driver and is marked; its next turn's dynamic prompt says the sandbox is blank. Idleness is the database's `updated_at`, not driver memory, so restarts do not reset it.
* **Turn checkpoint:** before a turn's first call that may change the sandbox (`permissions.touches_workspace`: edits, sandbox commands and git changes; never Slack or GitHub publishes, MCP tools or dynamic toolset tools), the registry snapshots every repository (`_checkpoint_before_first_change`). A turn that only talks, reads the web or acts on Slack, GitHub or MCP servers never starts a sandbox.
* **Tool loading** (`agent_core/tool_loading.py`, `TurnPolicy.tool_loading`, resolved by `api/services/tool_loading.py` from `general.tool_loading` / `tool_loading_threshold` and the agent's `tool_loading` / `active_tools`): the orchestrator computes the turn's deferred tools once (`_defer_tools`), leaves their definitions out of requests until loaded (`ToolRegistry.is_deferred`, `load_tools`, or a direct call), and appends their names, grouped by server, to the stable prompt. The list names every deferred tool, loaded or not, so loading never changes the cached prefix. Loaded names persist in session metadata (`loaded_tools`, `TurnCallbacks.tools_loaded`).
* **Scope and capability gates:** per-agent and per-skill tool whitelists, and a turn's `denied_tools` (`ExecutionContext.denied_tools`, from `TurnOverlay.denied_tools`: Slack's blocked tools), which are neither offered to the model nor run, whatever the whitelist. A transport allowed every tool passes no whitelist rather than a list of the tools registered before the turn, which would drop the turn's MCP tools; capability-tagged tools (e.g. `browser_inspect`) exist only when the session's sandbox has the capability.
* **Human gates** (`interaction.py`): `ask_question` and approvals pause the turn; the pending gate is stored with the turn (`api/turns/gates.py`) so a restart or another replica can continue it.
* **Dispatcher:** independent tool calls run in parallel; mutations of the same path are serialised. Each call takes a `ToolSlot` (`tool_slot.py`): a permit under its session's limit (`ROCKET_TOOL_MAX_CONCURRENCY`) and one under the process's (`ROCKET_TOOL_PROCESS_CONCURRENCY`), and a working-time budget (`ROCKET_TOOL_TIMEOUT_SECONDS`). Every wait for a person goes through `human_wait()` (the orchestrator's question and approval callbacks), which pauses the slot of the call it happens in: the permits are given back and the clock stops, so a question can wait for hours without timing out or starving other sessions. Answered or abandoned gates are forgotten (`DecisionGateManager.forget_*`).

**Context hygiene.** Tool output is clamped head-and-tail (`tools/clamp.py`). The request size is estimated from everything it sends (text, tool-call arguments, reasoning, images at ~1,600 tokens each, the tool schemas) and never below what the provider reported for the turn's previous request; the window comes from the organization's `models.context_windows`, else LiteLLM's model table, else a family default. Old verbose tool results are pruned to one-line receipts past 70% of the window; at 85% the history is compacted around invariant anchors: the system prompt, the request being worked on (the latest one the person wrote, kept verbatim), the checklist and the last steps (an assistant message with all its tool results, never split); a model summary of the rest, told the current goal first, replaces the middle. A request the provider still refuses as too large (`ContextWindowExceededError`, from LiteLLM's error) is compacted at once and retried, once. Assistant reasoning and `tool_call_id` pairing are never dropped (`transcript.py` repairs pairing on rehydrate).

**Subagents.** `SubagentRunner` runs a delegated, bounded ReAct cycle with its own history and a tool whitelist that can never include delegation. Roles come from the organization's configuration or built-in defaults; an unknown role gets read-only tools. Its tool calls go through the orchestrator's `ToolDispatcher.run_guarded` (the session's concurrency slots, the time budget, the per-file edit lock), and the registry applies the same permission mode and approvals. Its system prompt ends with `workspace_brief` (active repository, a fresh shell per command, clamped output, read-only when its tools are). When its steps run out mid-work, one tool-less call produces its report.

**Workspace layout.** `clone_repository` puts each repository in `/workspace/<name>`. `sandbox_driver/workspace.py` is the one rule for which folder a git, project or shell tool acts on: the folder the agent named (`path`, `cwd`) → the session's *active repository* → `/workspace` when it is a repository → the only repository under it; several and no choice is an error that names them. The active repository is set by the first clone (`ToolRegistry.remember_active_repository`, persisted in the session's metadata through `mutate_session`), carried to every turn on `TurnPolicy.active_repository` and kept on the execution context. `set_active_repository` replaces it (`choose_active_repository`). File tools resolve a relative path against it (`ToolRegistry.workspace_file`), so it names the same file as in `bash_exec`; `file_diff` events stay relative to `/workspace`. `GitEngine`, the publisher and the checkpoint routes use the same resolver; nothing ever runs `git init` on the agent's behalf.

**Edits.** `editor.py` applies exact block replacements and unified diffs and returns `FileDiff`s, which become `file_diff` events through one helper (`emit_file_diff`: once per change). `file_write`, `file_edit`, `apply_patch` and `apply_diff_file` report their own; around a `bash_exec` in a repository the changed files are fingerprinted (`tools/workspace_changes.py`: `git status` paths and blob hashes, before and after) and each file the command changed gets a diff against `HEAD` (up to 20).

## 4. The turn engine (`apps/api/src/api/turns/`)

Every transport (web socket, REST, Slack, GitHub webhook, scheduled mission, restart resume) ends in `run_guarded_turn` (`tasks.py`): it takes a global concurrency slot and the per-session write lock (a cluster advisory lock when replicas share a database), then runs `TurnRunner.run`:

1. **Prepare** — load the session, record the user message, write a durable `running` turn trace (so a crash is visible as `interrupted`), load governance, resolve persona, model route and turn budget (`routing.py`).
2. **Execute** — resolve model credentials (member key, organization key, platform key), bring the sandbox up blank (`provisioning.py`) and inject git credentials, build the system prompt (`prompt.py`: a byte-stable cached prefix plus a volatile suffix; the prefix is the agent's prompt, then the platform's runtime, workspace, editing, working-style and git sections (`git_guidance` per credential and signing mode, snapshotted in `tests/golden/system_prompt_git.json`), the skills and the active repository's instructions, remembered in session metadata `project_instructions` so a sleeping sandbox does not change the prefix), attach the turn's MCP tools and callbacks (`callbacks.py`), stream the orchestrator, translating each agent event into a published session event with one small handler per type (`events.py`).
3. **Record** — `finalise.py` stores the answer and trace with `store.mutate_session`, then publishes the closing `status_changed` with `final: true` — strictly after the answer is stored.
4. **Follow-up and cleanup** — `followup.py` suggests the next instruction; cleanup always runs.

`TurnContext` (`context.py`) is the data a turn carries; `shared.py` holds process-wide collaborators. A failure becomes an `error` event with `final: true` and an interrupted/failed trace, never a silent stop. After a restart, `turn_resume.py` continues turns the previous process left running (claimed by lease so exactly one replica resumes each).

## 5. Events, the WebSocket and consistency

**Events.** `SessionEvent(session_id, event_type, payload, seq)`; types are in `specifications/interfaces/events.py` and every payload has a `TypedDict` in `event_payloads.py`. With `ROCKET_VALIDATE_EVENTS=1` (set by `tests/conftest.py`) the in-process bus validates each published event and the test harness fails on a violation. `AsyncIOEventBus` serves one process and keeps a bounded replay window; `PostgresEventBus` shares events, sequence numbers and decisions across replicas.

**The session socket** (`SessionSocket`): authorise → open the live queue → note the sequence → read the session record → send one `sync` frame → stream. The rule that keeps it correct: the live queue is opened *before* the record is read, so nothing published afterwards can be missed. `sync.catch_up {from_seq, events}` starts at the in-flight turn's first `running` status and ends only at the runner's own closing event (`status_changed` with `final: true`); the orchestrator's earlier `completed` carries no such flag. The client rewinds its resume cursor to `from_seq` whenever a `sync` replaces its transcript (`lib/sync-plan.ts`) and ignores a REST read of the session that lands after the socket established it. Client frames that mutate (`turn`, `cancel`, `answer_question`, `approval`, `share`, …) are refused for read-only members. `resume` replays missed events from a cursor.

**Writes to a session record** go through `store.mutate_session(session_id, org, fn)` — a row-locked read-modify-write on PostgreSQL. A whole-record `get` + `update` lets the title task, the answer and the follow-up erase each other.

## 6. Sandboxes (`packages/sandbox-driver`)

`SandboxDriverProtocol` is the only way the platform touches a sandbox: `ensure_workspace`, `start_sandbox`, `hibernate_sandbox`, `destroy_workspace`, `get_status`, `exec_command` (timeout, env, streamed stdout), file read/write/list, `apply_patch`, `set_session_env`, `open_pty`, and `hold_awake`.

* **Docker driver** (local, single node): a named volume per session mounted at `/workspace`, a warm pool for fast starts, an inactivity reaper. A restricted organization's sandboxes join an internal network and reach the outside only through an allow-listing proxy that vets *resolved* addresses (so DNS rebinding cannot reach private ranges or the metadata endpoint).
* **Kubernetes driver** (production): one pod and one PVC per session in a dedicated namespace; hibernation deletes the pod and keeps the PVC; resume uses soft node affinity to the previous node to avoid multi-minute volume re-attach (soft rather than a hard `nodeSelector`, which would leave the pod `Pending` forever if that node is cordoned); pods are annotated against eviction while any command runs or background processes hold the sandbox awake (a per-session count of running commands, written to the pod only when the needed state changes); restricted organizations get a per-pod NetworkPolicy (the namespace policy excludes `rocket.chat/egress=restricted` pods because NetworkPolicies are additive). Storage classes: `gp3`, `managed-csi`, `pd-balanced`, or `standard`/`local-path`.
* **Fake driver:** deterministic and in-memory, for tests and CI.
* **Git gateway.** Sandboxes hold no GitHub credential: their git is pointed (by `GIT_CONFIG_*` environment, set each turn by `inject_git_credentials_into_sandbox`) at the API's `/v1/git/` routes, which stream git's smart-HTTP protocol to GitHub with a credential resolved on the platform. Reads only. `WorkspaceSpec.platform_endpoints` carries the gateway's `host:port` so the egress proxy (Docker) lets it through; the Kubernetes driver adds a rule for the API pods (`PlatformPeer`, from `ROCKET_PLATFORM_*`). `clone_repository` makes blobless partial clones (`--filter=blob:none --single-branch`).
* **Publishing** (`git_engine/publish.py`, `host_repo.py`): the sandbox computes the base and the new commits and makes `git bundle create HEAD ^<base>`; the platform reads it (`sandbox_driver.blobs.read_bytes`), fetches the base commit shallow and blobless into a temporary bare repository, imports the bundle, signs (`gpg_key`) or replays through GitHub's API (`github_app`), pushes, and moves the sandbox's branch onto the published commits when their hashes changed; `PublishResult.rewritten` lists each local commit's replacement, which `git_push` reports to the agent. Under the `co_authored` policy the member's `Co-authored-by` trailer is added to every commit GitHub re-creates (`PublishSpec.co_authors`), whatever made it.
* **Catalogue.** Each organization has a list of sandboxes (name, image, description, capability tags, one default) in `sandbox_catalogue`. A session starts in the entry chosen by name (`SandboxCatalogue.chosen`): the session's own (`metadata.sandbox_id`, from its creator), else its agent's `sandbox_id` when the session names no image either; otherwise the entry matching its image, else the default. Provisioning and the turn's capability check use the same rule; capabilities (e.g. `browser`) decide which optional tools exist for it.
* **Background processes.** `process_start/list/output/wait/stop` run dev servers and watchers in their own process group inside the sandbox (state files under `/tmp/rocket/proc/<id>/`, no daemon). The control plane mirrors them in `sandbox_processes` (`ProcessTracker`), announces `process_started`/`process_exited`, tells the agent at its next turn what exited while it was away, and holds the sandbox awake (`hold_awake`) while one runs.
* **Preview.** A minted, port-scoped token serves an app running in the sandbox through `/v1/preview/<token>/…` with a `sandbox` CSP, embedded in an iframe without `allow-same-origin`.
* **Terminal.** An interactive PTY over a WebSocket, gated like a write to the session and audited on open and close.

## 7. Models, configuration, integrations

**LLM gateway.** `LiteLLMGateway.chat_stream` is the single choke point for every model call (the loop, subagents, titles, summaries, follow-ups). Before the call it checks budgets (`BudgetService`, month-to-date from the persisted ledger) and resolves the key (member → organization → platform per `budgets.byok_policy`); after it, it writes one `usage_events` row. Retries and fallbacks are delegated to LiteLLM (`num_retries`, `fallbacks`) and never retried after tokens have streamed. Prompt caching marks only the stable prefix and tool schemas. Auxiliary calls use JSON-schema constrained output with one repair retry (`structured.py`). Model choice is decided above the gateway (routing settings). It asks for the usage block where the provider sends it only on request (`stream_options.include_usage`, when `litellm.get_supported_openai_params` lists it); without one, `llm_gateway.tokens.request_tokens` estimates the request (schemas, tool-call arguments, reasoning, images), the same count the context manager uses.

**Settings (`config-engine`).** A typed registry of domains (`general`, `models`, `budgets`, `routing`, `sandboxes`, `github`, `mcp`, `slack`, `governance`, `memory`, `user_preferences`); each key declares kind, default, scope (`org`, `user`, `both`), bounds and the file that consumes it (a test fails if the consumer does not read the key). Resolution is system default → organization value → member override, and an administrator can *lock* a member-overridable key. Writes are validated and rejected, never silently dropped. `doc/administer/settings-reference.md` is generated from the registry. Every key must have a behaviour test marked `@pytest.mark.setting("domain.key")` (enforced by `tests/unit/test_every_setting_is_wired.py`); a member preference must default to empty when it competes with an organization or platform default, otherwise the default counts as the member's choice and always wins.

**MCP.** Organization- and member-scoped servers (command/stdio for administrators only, HTTP/SSE/streamable-HTTP remote), secrets encrypted at rest, OAuth discovery and client registration through the MCP SDK, optional per-member authorisation, tools attached per turn. Presets for common servers are static data in the web app (`settings/mcp/presets.ts`) that only prefill the registration form.

**Command (stdio) servers and the MCP runner.** A command is an arbitrary program, so it runs neither in the API process nor in an agent sandbox but in the `mcp-runner` pod (`packages/mcp-runner`, optional, `MCP_RUNNER_URL`/`MCP_RUNNER_TOKEN`; without it stdio servers are unavailable and the UI says so via `GET /v1/mcp/runner`). One WebSocket (`/v1/stdio`, bearer-token authenticated) carries one server process: the first frame states the command, the environment, the organization and an optional install script; the runner builds a clean environment (never its own variables), starts the process in its own process group and relays newline-delimited JSON-RPC; closing the socket (the end of the turn, `McpToolProvider.aclose`) or `MCP_RUNNER_MAX_LIFETIME_SECONDS` kills the group. Capacity is bounded in total and per organization. There is deliberately no warm pool: an MCP server serves one client session and many reject a second `initialize`, so concurrent turns get one process each and nothing runs between turns; package caches (`/cache`) are what make starts cheap. An install script (`tools.py`) runs once per organization and script hash into `/cache/tools/<org>/<hash>`, without the server's variables, and that directory leads the server's `PATH`. Per-member values for overridable variables live encrypted in `mcp_member_tokens` under the key `env` (`mcp_member_env.py`); `_rows_with_member_env` merges them into a member-specific copy of the row for that member's turn and drops the server when a required value is missing. The probe/test path (`mcp_engine._probe_command`) uses the same runner, so a server is checked exactly as it will run.

**Sharing.** `routers/sharing.py` manages who can open a session: `is_shared` (organization-wide) and `collaborators` (user ids resolved from emails against the organization's users) on the record, plus an optional public link kept in `metadata.public_link` (`{id, url, expires_at}`). The link's token (`auth/share_token.py`, HS256, `typ=share`) names the session and the link id; revoking or replacing the link changes the stored id, so every older token fails verification. `GET /v1/shared/{token}` is exempt from the identity gate, re-checks `general.public_session_links`, and returns only user/assistant text. Writes use `mutate_session`.

**Tool calls written as text.** A model may put its native call syntax in the message text instead of a structured call (`agent_core/leaked_calls.py`). `_stream_model_step` hides it from the live stream (`LeakFilter`), and `_react_step` treats a reply with such markup and no real call as a failed step: it is left out of the conversation, a system notice asks for a proper call (`MAX_LEAK_RETRIES`), and after that the turn ends with a plain explanation. Add a marker there when a new model family does the same.

**Git.** `GitEngine` formats commits with `Co-authored-by` trailers, signs (GPG or GitHub App), opens pull requests, and verifies GitHub webhooks (HMAC; unsigned only if explicitly allowed). Webhook triggers (`issues.labeled` with the trigger label, addressed or labelled `issue_comment.created`, `pull_request`) are accepted only from repository insiders and an optional repository allowlist. Credentials are resolved per session (`resolve_session_git_credentials`: the App's read-only installation token when it can read the repository, else the member's linked account, else the deployment token) and injected into the sandbox; the member's own token stays host-side (`GitCredentialBundle.user_token`). **Publishing** is `GitEngine.publish_branch` (`git_engine/publish.py`), reached by the `git_push` and `git_open_pr` tools with a `PublishSpec` built from the member's *effective* policy (`effective_signing_policy`): `github_app` replays new commits through GraphQL `createCommitOnBranch` so GitHub signs them, `gpg_key` pushes commits the sandbox signed with the member's imported key (`git_signing.py`, validated by GnuPG; key injected per turn in a memory-backed keyring), `none` pushes as they are. The commit identity (`github_identity.commit_identity`) is the git panel override, else the GitHub login and primary or noreply e-mail. **Following pull requests:** `github_watches` (RLS-scoped) records which session follows which pull request or branch (created by `github_watch` or automatically after `git_open_pr`). `GitEngine.parse_repo_event` turns check-suite, review, comment and close events into `RepoEvent`s; `deliver_repo_event` fans one out to the live (not archived) sessions of the installation's organization as a `github_event`, then either starts a turn (`start_turn_on_session`, only for trusted authors, an idle session and under the per-watch wake cap) or keeps it for the next turn's dynamic prompt suffix.

**Memory, knowledge, skills.** Long-term memory (`remember`/`recall`, injected only into the volatile prompt suffix), pgvector knowledge bases, prompt skills and agent personas, all organization- or member-scoped under RLS.

**Missions** are scheduled sessions claimed atomically (`claim_due`) and run on a leader-elected scheduler; a run can report to a Slack channel.

## 8. Slack (`packages/slack-assistant`)

`SlackAssistant` is assembled from mixins that share the state declared in `state.py`: `toolset` (Slack tools and policy; `directory` adds the read-only people, user group, channel member and permalink tools, with `_readable_channel`: the current conversation, an allowlisted channel or a public one), `gates` (approval and question buttons, durable ownership), `admission` (rate limits, quotas, organization policy), `routing` (message classifier, sticky thread routes, private mode acknowledgement, ephemeral summary and sharing), `turn_stream` (run a turn and render events), `entrypoints` (the bot's slash command, the "Ask Rocket" shortcut, App Home, mission reports). `bot.py`, `stream.py`, `artifacts.py`, `health.py`, `block_kit.py` are plain helpers. Behaviour worth knowing:

* **Several bots:** An organization can run multiple bots, each representing an independent Slack app with its own `@handle`, sealed tokens (`slack_bots` table), policy overrides, and target agent or router. Each bot runs under per-bot leader election (advisory lock `slack:<bot_id>`).
* **Response modes:** `thread` (answers in thread with live progress) vs `private` (marks the request with a reaction, sends the requester an ephemeral link, runs in a private session, sends an ephemeral summary on completion, with a **Share in thread** button for voluntary sharing).
* **Bot manager** (`api/bootstrap/slack.py`, `SlackBotManager`): lists every organization's enabled bots on the schema-owner connection (a cross-tenant read, like the mission claimer) and runs one `SlackAssistant` per bot. `sync()` starts new bots, restarts changed ones (a hash of the record and tokens) and stops removed ones; the replica that saves a bot syncs at once, the others every 30 seconds. Sessions are `slack_<bot key>_<channel>_<thread>`, and a private request's adds `_<requester>`.
* **Router** (`api/services/slack_routing.py`): runs after admission and before any session exists, so a dismissed message creates nothing. The classifier model is resolved through the organization's model policy and the call runs under a `ModelScope` for the bot's organization, so it uses the organization's keys, caps and usage ledger. Structured output (`generate_structured`) by default; OpenRouter System One models (`services/systemone.py`) are called directly, so that path checks the caps and books the usage itself. Every decision is recorded in `slack_route_decisions` (RLS).
* One reply per request, streamed with Slack's agent streaming API (`stream.TurnStream`: `chat.startStream` on the first tool call, a `task_update` chunk per tool call, `chat.stopStream` with the answer and its footer); a turn without tools, or a workspace that refuses streaming, gets a plain reply. Long answers and diffs go out as files. Turns are stopped with the bot's slash command (`/<command> stop`), which only stops the caller's own turns.
* Slack does not namespace slash commands, so each bot has its own (`bot.command_for(handle)`, also in its manifest) and still answers the legacy `/rocket`.
* A thread's pending question survives restarts: the requester is stored on the session (`slack_turn_requester`) and a question whose turn died is answered from its stored copy.
* Socket Mode runs on leader replicas (advisory-lock election per bot); event redeliveries are dropped; a watchdog reconnects silent sockets.
* The Slack tools are registered once on the shared tool registry; each call runs on the live assistant of the bot whose session is executing (`toolset._LIVE_BOTS`, keyed by the bot's session key), so it uses that bot's client, policy and conversations, and a stopped bot's sessions are told Slack is not connected.
* The platform calls back into the assistant only through the callables passed at construction (`api/bootstrap/slack.py`), so the package never imports the API.

The client store is split into slices under `lib/store/` (sessions, agents, stream, composer, layout). `lib/websocket.ts` + `lib/sync-plan.ts` + `lib/session-cursor.ts` implement the resume/sync rules of §5. ## 10. Operations

* **Probes and metrics:** `/health` (liveness, no dependencies), `/v1/ready` (database ping, 503 while draining), `/metrics` (Prometheus text), `POST /v1/drain` (the Helm `preStop` hook). Shutdown sets `draining`, stops background tasks, closes the bus, the sandbox warm pool and the connection pool, in that order.
* **Backpressure:** a global concurrency gate bounds concurrent turns; a bounded registry of per-session locks gives one writer per session.
* **Replicas:** `ROCKET_EVENT_BUS=postgres` turns on the shared bus, cluster session locks, leader election (Slack socket, mission scheduler) and turn-lease recovery. Schema upgrades run at container start (`alembic upgrade head`); the API refuses to start against a schema that is behind.
* **Governance jobs:** a retention sweeper, turn-lease heartbeats and a remote-MCP refresh run on the schema-owner connection because they must see every tenant.
* **Packaging:** multi-stage Dockerfiles in `deploy/docker/`, Compose for evaluation and single-node production, the Helm chart in `deploy/helm/platform` (every new environment variable, secret, mount or route must be added there).
