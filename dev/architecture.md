# Architecture

How Rocket Chat is built, how a request becomes a finished turn, and where each responsibility lives. Rules for working in the code are in [`AGENTS.md`](../AGENTS.md); identity, isolation and secrets are in [`security-and-tenancy.md`](security-and-tenancy.md). End-user and operator documentation is the site in `doc/`.

## 1. Shape of the system

One control-plane process, one database, and sandboxes that are created on demand.

```
 Web cockpit (Next.js 15)      Slack (Socket Mode)      GitHub webhooks      Scheduled missions
        |  REST + WebSocket          | (in-process)           | HTTP               | (in-process)
        v                            v                        v                    v
 +--------------------------------------------------------------------------------------------+
 |  Control plane  (apps/api, FastAPI, one process per replica)                               |
 |  routers -> turn engine -> orchestrator (agent-core) -> tools                              |
 |                  |              |                          |                               |
 |            event bus       LLM gateway              sandbox driver (Docker | Kubernetes)   |
 |                  |         (LiteLLM, BYOK, budgets)        |                               |
 +------------------|---------------------------------------|-------------------------------+
                    v                                       v
          PostgreSQL 16 + pgvector                 One sandbox per session
          (row-level security, LISTEN/NOTIFY)      (container or pod + persistent workspace)
```

Design choices that shape everything else:

* **No worker tier.** A turn is a coroutine in the API process. Slack, the mission scheduler, the sandbox reaper, retention and turn-lease heartbeats are `asyncio` tasks in the same process (`api/bootstrap/`). Several replicas cooperate through PostgreSQL only: a shared event bus (`LISTEN`/`NOTIFY`), advisory locks for "one turn per session" and leader election, and claim-based work queues.
* **Contracts first.** Every subsystem is used through a protocol in `specifications/interfaces/` (sandbox driver, LLM gateway, session store, event bus, transcript store, git engine, plus the typed event payloads). `packages/` never import from `apps/`; `specifications` imports no workspace package (enforced by `tests/unit/test_import_boundaries.py`).
* **Sessions start blank.** A session is a sandbox with an empty `/workspace`. The agent finds and clones repositories itself (`clone_repository`); nothing is pre-cloned by the platform.
* **PostgreSQL is the only state.** Sessions, turn traces, transcripts, memory, audit, usage, settings, missions, processes and the sandbox catalogue are tables. With no `DATABASE_URL` (tests, a laptop) the same protocols are served by in-memory stores.

## 3. The agent (`packages/agent-core`)

**Orchestrator.** `AsyncReActOrchestrator` runs the reason-and-act loop. A turn is a `_TurnRun` driven through phase methods: `_begin_turn_run` → `_drive_turn` → `_react_step` (stream one model response, dispatch its tool calls, append results) → `_synthesize_after_budget` / `_fail_turn`. When the turn budget is spent while the model is still calling tools, one last tool-less step synthesises an answer from what was gathered (`post_failure_synthesis`), so findings are never left half-finished. `human_wait_scope` lets the process-wide concurrency gate release its slot while a turn waits for a person.

**Engine notes.** What the engine tells the model during a turn (budget notice, stale or unfinished checklist, "you wrote a tool call as text", the final-synthesis instructions) lives on the `_TurnRun` (`sticky_notes` for the rest of the turn, `next_notes` for the next request) and is rendered by `notes.py` at the end of the request as one user-role `<system-reminder>` block, merged into the last user message when the request ends with one (unless that message carries the cache breakpoint). Notes are never stored. Synthetic prompts (restart resume, continuations, wake turns) are passed with `synthetic_prompt=True`: the orchestrator stores them once in the model transcript as the turn's opener, a `<system-reminder>` marked as an automatic turn (`notes.automatic_turn_prompt`), never in the session history the cockpit shows. They are not re-sent at the end of every request: as the newest message on each step they read as a fresh instruction and models restarted the same first step in a loop. `_current_request` skips them to anchor context compaction on the last real user prompt, and memory recall queries the real prompt; the turn-fixed context is inserted after the opener (`find_turn_user_index`). A request's only `system` message is the leading stable prompt: LiteLLM's translation for several provider families moves every system message into the system prompt, so a stored mid-history notice would become a standing instruction. The gateway logs a warning if one slips through, and rehydration drops the system messages older transcripts stored.

**Request layout and prompt caching.** Request assembly is owned by `agent_core/context_policy.py` to enforce strict prompt-cache prefix stability:
1. The session-stable system prompt (the only `system` message, cacheable).
2. The conversation history up to the message that opened the turn (the person's, or an automatic turn's stored opener).
3. Turn-fixed context (`context_note`: routing notices, the active repository's instructions (`AGENTS.md`), background processes, GitHub activity, recalled memories, `.rocket/PLAN.md`/`PROGRESS.md` as they were at turn start; and user attachment manifests) inserted once right after that message in a `<system-reminder>` block. Because it stays in this position throughout the turn, requests 2..N share a byte-identical prefix.
4. The ReAct tool loop of the current turn (assistant tool calls and tool observation results).
5. Dynamic tail notices (budget warnings, checklist reminders, truncation notices) and images from `view_image` ride at the tail after the tool results, preventing retro-attachments that would invalidate the cached prefix of earlier steps.
6. The last stable conversation message carries a rolling cache breakpoint (`with_cache_breakpoint`).
User attachments are described via lightweight manifest rather than raw content dumping, enabling on-demand inspection via `file_read`. The turn trace records `usage.cache_hit_ratio`.

**Reasoning.** A step's reasoning text and, for providers that sign it, its reasoning blocks are kept on the assistant message that carries the step's tool calls (with any text the model wrote before calling). The gateway sends them back as each family requires (`reasoning_replay`): Anthropic-style extended thinking gets its signed `thinking_blocks` (and no `temperature`), DeepSeek gets `reasoning_content` within the current tool loop, other families nothing; Gemini's thought signatures already travel in LiteLLM's tool-call ids, which are kept as given.

**Execution context.** `current_execution_ctx` (a `contextvar`) carries the session, organization, user, event queue, permission mode, sandbox capabilities and per-turn callbacks. Tools and subagents read it; nothing mutates shared singletons across turns (`tests/unit/test_no_shared_turn_state.py`).

**Tools.** `ToolRegistry` (FastMCP-based) holds Tier 1 tools (in-process: web, knowledge base, GitHub reads, memory, planning, questions, delegation) and Tier 2 tools (run in the sandbox through the driver: files, search, shell, tests/lint/build, git, package manager, background processes, browser, image viewing). Built-in tools are registered in groups from `tools/builtin/<domain>.py`; their implementations are sibling modules. The registry is also the enforcement point:

* **Permission modes** (`permissions.py`, modes `plan`, `ask`, `auto_edit`, `auto` (default), `bypass`): every tool call is classified as read, edit, command or publish with a risk level, and the session's mode decides which classes raise a human gate *before* the tool runs (`ask` gates edits and commands, `auto_edit` gates commands and publishing). A call classified `critical` (merging a pull request, `github_api` `DELETE`, a hard `git_revert`, a shell command that wipes `/`, `~` or `/workspace`, `mkfs`, `dd` onto a device) is gated in every mode but `bypass`, so `auto` is not "no gates". Batched tools (`github_pull_request.actions`) are classified by their riskiest action (`requested_actions`). `plan` rejects every mutating tool server-side, whatever the model says.
* **GitHub tools** (`builtin/github.py`, `builtin/repository.py`; HTTP in `github_client.py`, pull requests in `github_prs.py`, Actions/releases/search in `github_ci.py`, `github_api` in `github_generic.py`) run on the platform: the sandbox holds no GitHub credential and its `gh` is a stub. Reads use `TurnCallbacks.github_access` (the session's read credential). Changes use `TurnCallbacks.github_write_access(repository)`, which `api/turns/callbacks.py` resolves per repository: the member under `pr_creation: as_user`, else the App installation mapped to the organization (`inherit_permissions`, not lowered to read), else the member. The `GithubAccess.actor` it returns is shown in each result. These tools carry an `action` (or, for `github_pull_request`, a list of `actions`) argument, so they are classified per call (`ACTION_CLASSIFIED_TOOLS`): read actions are reads, changes are publishes, and `merge` and `github_api` `DELETE` are critical (gated in every mode but `bypass`). `github_generic.py` holds the endpoint and mutation deny lists.
* **Sandbox types and workspace release:** a catalogue entry may name a placement profile (`sandbox_driver/profiles.py`, defined only by the operator in `K8S_SANDBOX_PROFILES`; the Kubernetes driver applies node selector, tolerations, runtime and priority class, labels, annotations, storage class and sizing, the Docker driver ignores it) and override CPU, memory and disk (precedence: agent > type > organization). `services/workspace_release.py` runs hourly on the schema-owner connection: a session whose sandbox is not running and whose record has not changed for its delay (`sandboxes.workspace_release_days` or the type's `release_after_days`) has its workspace destroyed through the driver and is marked; its next turn's dynamic prompt says the sandbox is blank. Idleness is the database's `updated_at`, not driver memory, so restarts do not reset it.
* **Turn checkpoint:** before a turn's first call that may change the sandbox (`permissions.touches_workspace`: edits, sandbox commands and git changes; never Slack or GitHub publishes, MCP tools or dynamic toolset tools), the registry snapshots every repository (`_checkpoint_before_first_change`). A turn that only talks, reads the web or acts on Slack, GitHub or MCP servers never starts a sandbox.
* **Context window.** `ContextManager.resolve_context_limit` answers with the organization's `context_windows`, else the catalogue's spec (`services/model_catalogue.resolve_model_spec`: the provider's live listing from `services/provider_catalogue.py`, then LiteLLM, then the model's family), else LiteLLM, else the family, else 128K flagged `default`. A spec whose source is `default` is never an answer, so a model nobody knows reaches the later sources. `context_target_tokens` caps the window the tiers work against; `threshold(limit, ratio, reserve)` keeps `max_tokens` of room for the reply below the window (never below half of it). The provider listing is refreshed by `BackgroundServices` and by the model picker's own fetch.
* **Shell commands and dedicated tools.** `tools/shell_intent.py` classifies a `bash_exec` command as a search, read, list or edit that `grep_search`, `file_read`, `glob_files` or `file_edit` also does (the first stage of a pipeline only, so `go test | tail` is never flagged). `bash_exec` appends a one-line tip to its result from the second such call of a turn and then every third; the command always runs. `pace.py` also reminds a turn that keeps failing on its environment (credential, network, permission), that rewrites git remotes, or that keeps reading dependency source.
* **Tool loading** (`agent_core/tool_loading.py`, `TurnPolicy.tool_loading`, `api/services/tool_loading.py`): every request carries `CORE_TOOLS` (`specifications/interfaces/agent.py`, nineteen tools), the loading tools and the agent's `active_tools` (names or patterns), each only when the agent may use it, and the tools switched on for the turn (a toolset's, a sandbox capability's: `ToolRegistry.enabled_for_this_turn`); every other allowed tool is deferred (`deferred_names`), and the loading tools are then allowed whatever the agent's list says. `ToolLoading.send_all` is the default for an orchestrator driven without the platform's policy. A turn with no agent sends everything (`ToolLoading.send_all`). Migration `050_core_tool_set` removed the former modes (`all`, `on_demand`, `pinned`, `auto`), the agents' `tool_loading` column and the `general.tool_loading*` settings, keeping each agent's pins as its active tools. The orchestrator computes the turn's deferred tools once (`_defer_tools`), leaves their definitions out of requests until loaded (`ToolRegistry.is_deferred`, `load_tools`, or a direct call), and appends their names, grouped by server, to the stable prompt. The list names every deferred tool, loaded or not, so loading never changes the cached prefix; a server with more than `COMPACT_SERVER_FROM` tools is listed under its `mcp__<server>__` prefix and `load_tools` resolves the short names (`resolve_tool_name`). Loaded names persist in session metadata (`loaded_tools`, `TurnCallbacks.tools_loaded`). The prompt's guidance follows what is sent (`PromptTools.sends`): a deferred tool's guidance is in its own description, which arrives when it is loaded. `POST /v1/tools/loading-preview` gives the agent settings page the counts, and it warns past `ACTIVE_TOOLS_WARNING` (30); `POST /v1/agents/lint` (`services/persona_lint.py`) warns about a prompt over 4,000 characters, an unknown tool or an argument a tool does not take.
* **Session usage** (`api/services/session_usage.py`, `GET /v1/sessions/{id}/usage`): totals, per-turn and per-model figures computed from the usage ledger, which records every model call as it happens, so a turn that is still running is counted (its trace only receives its tokens when it ends). A call belongs to the turn that started last before it (so the title, summary and follow-up calls count with the turn that caused them); per-turn figures need the turn traces (PostgreSQL), the totals do not. The cockpit (`SessionUsageChip`, `useSessionUsage`) reads it when a session opens, every eight seconds while a turn runs and once when it ends. Each finished turn also carries `metrics` (`TurnMetrics` in `services/turn_trace.py`, stored in `turn_traces.tokens.metrics`): steps, model and tool time, reasoning (total and longest step), reasoning-limit stops, the fixed overhead of a request (system prompt and tool definitions, counted once per distinct set by `_overhead_figures`, with the system and tool parts separately and the number of tools sent), the context window the hygiene worked against and its source, shell commands that a dedicated tool covers, `load_tools` calls, pushes and compactions. The orchestrator puts a step's duration, reasoning length and overhead on its internal `model_usage` event; the trace folds them. **Measuring the harness:** `tests/unit/test_request_budget.py` holds the fixed part of a coding request to a reviewed snapshot; `scripts/harness_bench.py` runs the live tasks of `tests/harness/live/` (or replays a session) through the REST API and compares these metrics with a baseline (`.github/workflows/live-bench.yml`, nightly and manual).
* **Standing instructions** (`agent_core/standing.py`, `agent_core/skill_blocks.py`): an instruction skill arrives as the result of `execute_skill`: one `<skill name=…>` block, where the agent asked for it (as Claude Code delivers skills). Pruning never turns that result into a receipt (`is_skill_result`), and a compaction re-attaches every skill block of what it replaces (`skill_blocks`, within 20,000 characters per skill and 30,000 together, most recent first), so neither can take the instructions away; loading the same text again answers that it is already in the conversation. The session records what it loaded (`skills_read`, `TurnCallbacks.skills_read`, with the digest of the text) and `api/services/skills_in_effect.py` re-resolves it each turn: the context note carries only a skill the conversation lacks (a session from when skills were rendered into every note) and a one-line notice for a skill edited since it was read. A freshly cloned repository's `AGENTS.md` is still state rendered into the turn's context note (`standing_pending`): a clone returns the instructions apart from its message (`CloneOutcome.instructions`) and is quiet (`--quiet`); a long file keeps its start and end (`clamp_instructions`). Subagents keep their own state and read the skill in the result.
* **Pace reminders** (`agent_core/pace.py`): derived from the conversation like the checklist reminder, a note after ten steps of a turn without a file change (decide, implement, build and test in the sandbox) and after four consecutive single reads (batch them); skipped in plan mode. The working-style prompt asks for the same, and `models.default_reasoning_effort` lets an organization set how much a model that the catalogue does not know reasons. A third reminder fires every third look into a dependency's source (`go/pkg/mod`, `node_modules`, `site-packages`, ...). **Reasoning effort** is mapped before the request leaves: `api/services/openrouter_efforts.py` caches OpenRouter's per-model `supported_efforts` and `turn_service` rounds the requested level onto one the model takes (`none` turns reasoning off: an effort for OpenRouter, nothing for other providers). **The reasoning guard** (`agent_core/reasoning_guard.py`): `_StreamCollector` raises `StepReasoningOverrunError` when a step's estimated reasoning passes `models.reasoning_step_limit_tokens` before any text or tool call; `_stream_model_step` records the stopped call's usage (`finish_reason: reasoning_limit`) and repeats the step once with reasoning off and a decide-now note. It bounds one step's deliberation, never the turn.
* **MCP server guidance** (`agent_core/guidance.py`, `TurnPolicy.mcp_guidance`, `McpServerEntityModel.guidance`): the first line of a server's markdown guidance is its *trigger*, listed with the server name in the stable prompt (`render_index`, built in `_defer_tools` beside the deferred-tool list, so it never changes within a session); the text is *put in effect* (`put_in_effect`) when the agent loads a tool of the server (`load_tools`) or calls `load_guidance`, once per session and per digest. Whatever is in effect is rendered into the turn's volatile context note, never into the conversation (tool results are pruned to receipts and summarized away): at the start of a turn from session metadata (`guidance_read`, `TurnCallbacks.guidance_read`) plus short texts of servers with a loaded tool (`in_effect_at_turn_start`), and mid-turn by moving `ExecutionContext.guidance_pending` into `_TurnRun.context_note` after each tool step. `ToolRegistry.call_tool` refuses a tool of a guided server whose guidance is not in effect, before the approval prompt. Bounds: 8,000 characters per server (API validation), 16,000 in effect together (the longest-unused is dropped and must be read again), 1,500 for automatic effect. A turn with no guided server carries no `load_guidance` tool (`denied_tools`) and no text at all. **Essential tools** (`tool_loading.ESSENTIAL_TOOLS`: `load_tools`, `search_tools`, `load_guidance`, `exit_plan_mode`) are the tools a platform gate sends the agent to when it refuses a call; no agent tool list, Slack allowlist, channel profile or Slack blocklist can remove them (`ToolRegistry._scope_tool_blocked`, `_allowed_tools`, `_slack_tool_selection`), and each is still offered only when it has work (deferred tools, guidance, plan mode). A gate that tells the agent to call a tool must add that tool to this set, or an older agent list turns the instruction into a dead end. Subagents copy the context with their own empty state and read the text in the `load_guidance` result; they never write the session's record. `POST /v1/tools/loading-preview` runs `deferred_names` for the agent settings page.
* **Scope and capability gates:** per-agent and per-skill tool whitelists, and a turn's `denied_tools` (`ExecutionContext.denied_tools`, from `TurnOverlay.denied_tools`: Slack's blocked tools), which are neither offered to the model nor run, whatever the whitelist. A transport allowed every tool passes no whitelist rather than a list of the tools registered before the turn, which would drop the turn's MCP tools; capability-tagged tools (e.g. `browser_inspect`) exist only when the session's sandbox has the capability.
* **Human gates** (`interaction.py`): `ask_question` and approvals pause the turn; the pending gate is stored with the turn (`api/turns/gates.py`) so a restart or another replica can continue it. Loop detection never pauses an autonomous turn: repeated failures and edit/revert oscillations become a note to the model in every mode but `ask` (`_handle_progress_decision`), and a call repeated with an unchanged result carries a notice in its result (`repeats.unchanged_repeat_note`); an unchanged checklist re-send is a no-op (`ExecutionContext.checklist`).
* **Steering and queued messages** (`AgentOrchestratorProtocol.steer`, `SteeringMessage`, `services/queued_messages.py`): a message sent while a turn of the session runs (here or on another replica: `is_running`, or the record's `is_processing`) is stored in `session_queued_messages` (forced RLS, migration `052`) by `hold_for_running_turn`, announced as `message_pending`, and has a `delivery`. `steer` also hands it to a turn running in this process, which takes it at its next step as a user message of the conversation (`_take_steering`); the runner's `user_steer` handler saves the turn so far as an assistant entry, then the message, marks the row `taken` and broadcasts `user_message`. `queue` waits for the end of the turn. When a turn ends, `TurnRunner._start_queued_turns` claims every pending row of the session in one `UPDATE … RETURNING` and starts them as the next turns, one each, in order; a row stranded by a restart or another replica is started by the queued-messages sweeper (`stranded_sessions`, after a minute, when no turn runs). `cancel_message` or `DELETE /v1/sessions/{id}/queued-messages/{message_id}` withdraws a pending one (`message_cancelled`, `withdraw_steering`). The platform prompt tells the agent to treat mid-work messages as steering unless they clearly replace the task.
* **Repository setups** (`services/repository_setups.py`, `repository_setups` table, forced RLS, migration `051`, `/v1/repository-setups`, admins only): an organization's commands for a folder of a repository (patterns on `owner/name` and on the folder, matched segment by segment). Before a command tool (`FOLDER_COMMAND_TOOLS`) runs, the registry asks the turn to prepare its folder (`TurnCallbacks.prepare_folder`, once per folder and turn, `ExecutionContext.prepared_folders`); matching setups not yet run there run through `repo_setup.run_setup` (its per-directory marker makes it once per workspace, again when the commands change) with the agent's environment. A failure stops the command and returns the output (`FolderSetupOutcome`).
* **Dispatcher:** independent tool calls run in parallel; mutations of the same path are serialised. Each call takes a `ToolSlot` (`tool_slot.py`): a permit under its session's limit (`ROCKET_TOOL_MAX_CONCURRENCY`) and one under the process's (`ROCKET_TOOL_PROCESS_CONCURRENCY`), and a working-time budget (`ROCKET_TOOL_TIMEOUT_SECONDS`). Every wait for a person goes through `human_wait()` (the orchestrator's question and approval callbacks), which pauses the slot of the call it happens in: the permits are given back and the clock stops, so a question can wait for hours without timing out or starving other sessions. Answered or abandoned gates are forgotten (`DecisionGateManager.forget_*`).

**Context hygiene.** Tool output is clamped head-and-tail (`tools/clamp.py`). Tool outputs exceeding `general.output_offload_threshold` (default 6,000 chars) are offloaded to `/workspace/.rocket/outputs/{turn}_{call_id}.txt` while preserving a head/tail excerpt in the active prompt (lines are cut at 400 characters and an excerpt that is still too long is cut by characters). The in-memory copy that serves sandbox-free tools is bounded by bytes per session and overall, least recently used first, and released when the session is deleted; files older than two days are removed once per session per process (`tools/offload.py`). The request size is estimated from everything it sends (text, tool-call arguments, reasoning, images at ~1,600 tokens each, the tool schemas) and never below what the provider reported for the turn's previous request; the window comes from the organization's `models.context_windows`, else LiteLLM's model table, else a family default. The thresholds apply to the smaller of the window and the organization's working context size (`models.context_target_tokens`, 200,000 by default; a 1M-token model otherwise worked for hundreds of steps at half a million tokens per request). Old verbose tool results are pruned to one-line receipts past 70% of it (a receipt names the tool and, when the output was offloaded, the file holding it; the long string arguments of older calls, such as the content of a `file_write`, are replaced by their size, keeping the call's JSON valid); at 85% the history is compacted around invariant anchors: the system prompt, the request being worked on (the latest one the person wrote, kept verbatim), the checklist, session working-memory state (`.rocket/PLAN.md` and `.rocket/PROGRESS.md`, backed up to session metadata and restored across pod lifecycles), and the last steps (an assistant message with all its tool results, never split). The rest becomes one bridge carrying every earlier message of the person verbatim (up to about 20,000 tokens, newest kept first, as Codex keeps them), the skill blocks it replaced, and a checkpoint summary. **The summary** (`agent_core/compaction_summary.py`, `agent_core/summarizer.py`) is asked on the live request, as opencode and Codex do: the same model, system prompt, tools and history, plus the summary prompt (opencode's template: Objective, Requirements, Decisions, Work State, Next Move, Relevant Files, Important Context; an update prompt when the history already holds a checkpoint), with `tool_choice: none`, reasoning off and 12,000 output tokens, so the provider serves the prefix from its cache. A summary model other than the turn's, or a live request the provider refuses, gets a flattened transcript instead. The answer is checked (`valid_summary`: not empty, no tool-call markup, the Objective and Next Move headings) and asked for once more with a stricter note; when both fail, `tool_history_digest` rebuilds the record from the tool calls (files changed, commands and exit codes, commits, pushes, pull requests, waits). The outcome is `summary_status` (`model`, `model_retry`, `digest`; `legacy` before migration `049`) on the checkpoint and the `context_compacted` event, and the cockpit's card says when the summary was rebuilt. A bridge merged into the next request is handed to the following compaction, so what it carried is carried again. Compaction checkpoints are durably stored in PostgreSQL (`session_compactions` table, forced RLS) with hysteresis guards (minimum step cooldown) so crashed or restarted turns rehydrate without loss or recompaction loops. One compaction routine (`ContextManager._compact`) serves the orchestrator, the manual `/compact` route and subagents; the synchronous hygiene entry points that duplicated it were removed. A request the provider still refuses as too large (`ContextWindowExceededError`) is compacted at once and retried, once. Assistant reasoning and `tool_call_id` pairing are never dropped (`transcript.py` repairs pairing on rehydrate).

**Subagents.** `SubagentRunner` runs a delegated ReAct cycle with its own history and a tool whitelist that can never include delegation. A role's `max_turns` (default 30; `0` = until it finishes, with a final tool-less report when a limit is reached) is a per-role setting, and each step runs the same pruning and compaction as the main agent (`_keep_context_small`); the saved transcript keeps every message (`_record`) even when the live conversation was compacted. Roles come from the organization's configuration or built-in defaults; an unknown role gets read-only tools. Delegates return typed `SubagentTaskResult` records (`artefacts`, `changed_files`, `status`, `tokens`, `cost`, `duration_ms`), and full subagent transcripts are durably persisted in PostgreSQL (`subagent_transcripts` table, forced RLS) and accessible via REST (`/v1/sessions/{id}/subagents`). Parallel write delegates (`delegate_subagents_parallel`) require a sandbox profile with $\ge 2$ CPU and $\ge 4$ GiB RAM (`has_parallel_write_capacity`); on smaller profiles, execution is automatically serialized to prevent compiler and build OOMs. Each delegate operates in an isolated `ExecutionContext` and git worktree under `.rocket/worktrees/<id>`.

**Multi-repository workspace & commands.** For workspaces spanning multiple repositories, `workspace_status` detects dependencies across package manifests (`package.json`, `go.mod`, `pyproject.toml`, `Cargo.toml`), topologically sorts them, writes `/workspace/.rocket/workspace.json`, and injects a $\le 10$-line workspace summary into turn-fixed context. `git_status_all` and `repo_foreach` allow cross-repo status tracking and batch command execution with clamped outputs and fail-fast aborts.

**Workspace layout.** `clone_repository` puts each repository in `/workspace/<name>`. `sandbox_driver/workspace.py` is the one rule for which folder a git, project or shell tool acts on: the folder the agent named (`path`, `cwd`) → the session's *active repository* → `/workspace` when it is a repository → the only repository under it; several and no choice is an error that names them. The active repository is set by the first clone (`ToolRegistry.remember_active_repository`, persisted in the session's metadata through `mutate_session`), carried to every turn on `TurnPolicy.active_repository` and kept on the execution context. `set_active_repository` replaces it (`choose_active_repository`). File tools resolve a relative path against it (`ToolRegistry.workspace_file`), so it names the same file as in `bash_exec`; `file_diff` events stay relative to `/workspace`. `GitEngine`, the publisher and the checkpoint routes use the same resolver; nothing ever runs `git init` on the agent's behalf.

**Edits.** `editor.py` applies exact block replacements and unified diffs and returns `FileDiff`s, which become `file_diff` events through one helper (`emit_file_diff`: once per change). `file_write`, `file_edit`, `apply_patch` and `apply_diff_file` report their own; around a `bash_exec` in a repository the changed files are fingerprinted (`tools/workspace_changes.py`: `git status` paths and blob hashes, before and after) and each file the command changed gets a diff against `HEAD` (up to 20).

## 4. The turn engine (`apps/api/src/api/turns/`)

Every transport (web socket, REST, Slack, GitHub webhook, scheduled mission, restart resume) ends in `run_guarded_turn` (`tasks.py`): it takes a global concurrency slot and the per-session write lock (a cluster advisory lock when replicas share a database), then runs `TurnRunner.run`:

1. **Prepare** — load the session, record the user message, write a durable `running` turn trace (so a crash is visible as `interrupted`), load governance, resolve persona, model route and turn budget (`routing.py`).
2. **Execute** — resolve model credentials (member key, organization key, platform key), bring the sandbox up blank (`provisioning.py`) and inject git credentials, build the system prompt (`prompt.py`: a byte-stable cached prefix plus a volatile suffix; the guidance sections are built from the tools the turn can call (`PromptTools`: the agent's list, the transport's denied tools), so a read-only agent is not told to edit and a Slack thread that denies `git_push` is told publishing is unavailable; the whole default prompt is snapshotted in `tests/golden/system_prompt_default.txt`; the prefix is the agent's prompt, then the platform's runtime, workspace, editing, working-style and git sections (`git_guidance` per credential and signing mode, snapshotted in `tests/golden/system_prompt_git.json`) and the skills; the active repository's instructions go in the per-turn suffix (remembered in session metadata `project_instructions` so a sleeping sandbox still sends them), since in the prefix every repository switch made the next turn re-send the whole history uncached), attach the turn's MCP tools and callbacks (`callbacks.py`), stream the orchestrator, translating each agent event into a published session event with one small handler per type (`events.py`).
   A step that calls tools publishes a `running` status whose message is derived from the tool names (`agent_core/step_status.py`), never from the model's text: that text streams as `token` events and is already in the conversation, and the clients show the status as the one-line "now" indicator.
3. **Record** — `finalise.py` stores the answer and trace with `store.mutate_session`, then publishes the closing `status_changed` with `final: true` — strictly after the answer is stored.
4. **Follow-up and cleanup** — `followup.py` suggests the next instruction; cleanup always runs. Intermediate continuation turns suppress memory distillation and AI titling.

`TurnContext` (`context.py`) is the data a turn carries; `shared.py` holds process-wide collaborators. A failure becomes an `error` event with `final: true` and an interrupted/failed trace, never a silent stop. After a restart, `turn_resume.py` continues turns the previous process left running (claimed by lease so exactly one replica resumes each) via synthetic turns (`synthetic_prompt=True`), ensuring no duplicate user rows in history. A running turn keeps its answer and tool calls in memory and writes them into the session history only when it ends, so `services/interrupted_work.py` rebuilds an interrupted turn's entry from its trace (each completed call with the reasoning that led to it, saved as it finished) and the transcript (assistant text, and calls with no result, shown as `interrupted`); it runs before every resume pass (start-up, lease loop), is idempotent per trace (`interrupted_turns_saved` in session metadata) and also clears the session's `is_processing` flag, which only a turn's own cleanup clears. `hold_for_running_turn` decides whether to queue a message from the turn's trace, not that flag, so a session whose process died never queues for a turn that does not exist. The resume instruction names where the previous turn stopped (recent calls, the call with no result, its last reasoning), kept short because it is re-sent on every step. The reasoning of a model step that was still streaming when the process stopped was never saved and cannot be recovered.

**Long-running sessions.** A step limit of `0` (`NO_STEP_LIMIT`, `combine_step_limits`) runs a turn until the model answers, it is cancelled or a cost cap is reached, with no convergence notice or forced synthesis. `AGENT_MAX_TURNS` is the deployment default (read in `services/turn_limits.deployment_max_turns` and handed to the orchestrator; agent-core never reads it).

**Goal governance and continuation.** Tasks exceeding a turn's step limit automatically spawn continuation turns when `.rocket/PLAN.md` has remaining uncompleted items (`check_and_schedule_continuation`). Multi-turn budgets are tracked in `session_goals` (forced RLS) with cap surfacing and cancellation (`GET/POST /v1/sessions/{id}/goals`). The ceilings are settings: `budgets.max_continuations`, `budgets.goal_max_total_tokens` and `budgets.goal_max_wall_time_minutes`, beside the per-session `session_budget_usd` and the per-turn `budgets.max_turn_cost_usd` (`TurnPolicy.max_turn_cost_usd`).

**Verification.** ReAct loops enforce Plan -> Execute -> Verify workflow gates (`verification_gate_notice`), reminding the agent once per turn to verify what *this* turn edited (back to the latest user message; a shell test/build command, publishing (`git_push`, `git_open_pr`, after which the session follows CI), `wait_for ci_status` or reading a pull request's checks count), running only a check that already works and never setting up a toolchain for it.

**Waits.** The `wait_for` tool pauses execution on external conditions (`ci_status`, `review`, `process_exit`, `time`). Its callback returns a `WaitOutcome`: only a registered wait sets `ExecutionContext.wait_registered`, and only that ends the turn (`_wait_registered`); a wait that settled at once is a result the agent acts on in the same turn. A `ci_status` wait is about one commit: the `sha` given, else the head the session last published on the pull request's branch (`git_push` reports it through `TurnCallbacks.branch_published`; session metadata `pushed_heads`, `services/github_watches.pushed_head`). `_check_github_ci_poll` reads that commit's checks and answers `stale` while the pull request still points at an older head (GitHub moves it seconds after a push), so `_ci_already_settled` answers at once only when CI has finished on that commit or no check appears; a `check_suite` webhook carries `RepoEvent.head_sha`, and one about an older commit is announced without waking the session (`github_events._about_an_older_commit`). Durable waits persist in `session_waits` (forced RLS), are swept by a periodic background claimer (`claim_due_waits`) and closed by `settle_waits` when a newer wait on the same target replaces them, when their result wakes the session, or when the session is stopped (`DELETE /v1/sessions/{id}/turns`). They emit `wait_started` (with `sha` when one was named) / `wait_completed`, yield concurrency slots and wake turns on webhook, timeout or process events (`GET/POST /v1/sessions/{id}/waits`); the sweeper wakes a session once for all of its due waits (`group_waits_by_session`, `wake_prompt_for`), a CI wait that ran out saying what to check rather than only that it expired. **Post-edit diagnostics** (`tools/lsp.py`) tell a module-resolution failure (generated code or dependencies missing) from an error in the edited file: once per turn, as a note that the project is not set up.

**Compaction checkpoints and artifacts.** Manual and automatic context compaction stores checkpoints in `session_compactions` (`GET/POST /v1/sessions/{id}/compact`). Artifacts (`session_artifacts`, with every saved version in `session_artifact_versions`, both forced RLS) are copied across forks and published as `artifact_created`/`artifact_updated`; content is capped (`MAX_ARTIFACT_CONTENT_CHARS`) and the agent is told when it was cut. `update_artifact` takes whole content or exact `edits`.

**Code search and project memory.** On cloning repositories, project-specific build/test instructions are recalled from long-term memory with repository scoping. Semantic code search (`code_index.py`) indexes and boosts definition chunks (functions, classes, interfaces, structs) for improved code retrieval.

## 5. Events, the WebSocket and consistency

**MCP sign-in.** `api/services/mcp_oauth_setup.py` settles a server's OAuth before each sign-in: endpoints and `resource` from the server's metadata (`mcp_discovery.discover`, RFC 9728/8414), and a client from `establish_client` (RFC 7591 registration first, since it needs no inbound access; else a client ID that is the URL of our metadata document, `/v1/mcp/oauth/client-metadata.json`, exempt from auth). A client is tied to the callback URL it was set up for (`oauth_registered_redirect_uri`, built from `auth/origin.public_origin`, never `request.base_url`, which behind the web app's proxy is the backend's internal address) and set up again when it changes; one entered by hand (`oauth_client_method = manual`) is kept. At turn time `mcp_turn._mcp_tools_for_turn` returns `McpTurnTools(provider, needs_sign_in)`: OAuth servers without a working account are not connected but named in the prompt's dynamic part, and a server refusing its token (HTTP 401, `mcp_runtime.is_unauthorized`) is refreshed and listed again once (`McpToolProvider.retry`) before being marked `needs_sign_in`.

**Reasoning in the history.** The runner saves each step's reasoning on the first tool call of the step (`tool_calls[i].reasoning`, `TurnEventHandlers._take_step_reasoning`) and keeps on the answer only the reasoning after the last call (`TurnState.reasoning_attached`); the cockpit (`convertHistoryToFlightLogs`, and the `running_turn` steps of a `sync`) shows each before its step. Older turns, with all reasoning on the answer, show it before the steps.

**Events.** `SessionEvent(session_id, event_type, payload, seq)`; types are in `specifications/interfaces/events.py` and every payload has a `TypedDict` in `event_payloads.py`. With `ROCKET_VALIDATE_EVENTS=1` (set by `tests/conftest.py`) the in-process bus validates each published event and the test harness fails on a violation. `AsyncIOEventBus` serves one process and keeps a bounded replay window; `PostgresEventBus` shares events, sequence numbers and decisions across replicas. **Live command output.** The dispatcher gives each tool call a `LiveOutput` (`agent_core/tools/live_output.py`, reached by tools through the `current_live_output` contextvar and `live_chunk()`); the command tools hand it to the driver as `on_stdout_chunk` (stdout and stderr, possibly from a worker thread). It batches whole lines (~100 ms or 2,000 characters), redacts them, stops after 200,000 characters and puts `command_output` agent events on the turn's queue; `TurnEventHandlers._command_output` publishes them as `log_chunk` events carrying `tool_call_id`, and a call that streamed does not publish its result a second time. Streaming `token` and `reasoning_token` deltas are coalesced by `TokenCoalescer` into ~400-character or ~100 ms chunks (one flush at a time, the timer's included, so no chunk is lost or reordered), flushed immediately upon switching token kind or before any non-token event to preserve strict causal ordering while reducing bus write amplification.

**The session socket** (`SessionSocket`): authorise → open the live queue → note the sequence → read the session record → read running turn state → send one `sync` frame → stream. The rule that keeps it correct: the live queue is opened *before* the record is read, so nothing published afterwards can be missed. `sync.catch_up {from_seq, events}` starts at the in-flight turn's first `running` status (or the sequence of the latest completed tool step) and ends only at the runner's own closing event (`status_changed` with `final: true`); the orchestrator's earlier `completed` carries no such flag. `sync.running_turn` transmits the in-flight turn metadata and completed steps (redacted and recorded with their event `seq` on `turn_traces`), enabling tabs connecting or refreshing mid-turn to restore the complete flight log. The client rewinds its resume cursor to `from_seq` whenever a `sync` replaces its transcript (`lib/sync-plan.ts`) and ignores a REST read of the session that lands after the socket established it. Client frames that mutate (`turn`, `cancel`, `answer_question`, `approval`, `share`, …) are refused for read-only members. `resume` replays missed events from a cursor.

**Writes to a session record** go through `store.mutate_session(session_id, org, fn)` — a row-locked read-modify-write on PostgreSQL. A whole-record `get` + `update` lets the title task, the answer and the follow-up erase each other.

## 6. Sandboxes (`packages/sandbox-driver`)

`SandboxDriverProtocol` is the only way the platform touches a sandbox: `ensure_workspace`, `start_sandbox`, `hibernate_sandbox`, `destroy_workspace`, `get_status`, `exec_command` (timeout, env, streamed stdout), file read/write/list, `apply_patch`, `set_session_env`, `set_session_env_layer`, `open_pty`, and `hold_awake`.

* **Deployment variables and settings.** A deployment variable is a default below the settings, never above them: `SANDBOX_CPU_LIMIT`/`SANDBOX_MEMORY_LIMIT` only fill what the session's resources (organization, sandbox type and agent) leave unset. A variable with retired aliases is read with `config_engine.environment.env_value`, which logs the alias once; `scripts/check_docs.py` fails when the code reads a variable `doc/install/configuration.md` does not document.
* **Command environment.** Every command gets, lowest precedence first: the language caches (`DEFAULT_SANDBOX_CACHE_ENV`), the sandbox type's variables (layer `sandbox_type`, from `sandbox_catalogue.env`, secrets sealed with `CredentialCipher` and write-only through the API), the agent's own (layer `agent`, set by `env_set`/`env_unset` and kept in session metadata `agent_env`), the platform's (`set_session_env`: git gateway and credentials, which neither layer can override), then the call's own. Drivers keep layers in memory only, so `turns/runner._with_sandbox_type` hands both to the driver at every turn (`services/session_env.apply_session_env`); the prompt names the variables, never their values. Names are checked by `specifications.interfaces.sandbox.session_env_name_problem` (no `PATH`, `HOME`, `GIT_*`, `ROCKET_*`, `LD_*`…). Commands run in bash when the image has it (`utils.wrap_with_deadline`).

* **Docker driver** (local, single node): a named volume per session mounted at `/workspace`, a warm pool for fast starts, an inactivity reaper. A restricted organization's sandboxes join an internal network and reach the outside only through an allow-listing proxy that vets *resolved* addresses (so DNS rebinding cannot reach private ranges or the metadata endpoint).
* **Kubernetes driver** (production): one pod and one PVC per session in a dedicated namespace; hibernation deletes the pod and keeps the PVC; resume uses soft node affinity to the previous node to avoid multi-minute volume re-attach (soft rather than a hard `nodeSelector`, which would leave the pod `Pending` forever if that node is cordoned); pods are annotated against eviction while any command runs or background processes hold the sandbox awake (a per-session count of running commands, written to the pod only when the needed state changes); restricted organizations get a per-pod NetworkPolicy (the namespace policy excludes `rocket.chat/egress=restricted` pods because NetworkPolicies are additive). Storage classes: `gp3`, `managed-csi`, `pd-balanced`, or `standard`/`local-path`.
* **Fake driver:** deterministic and in-memory, for tests and CI.
* **Git gateway and clones.** Sandboxes hold no GitHub credential: their git is pointed (by `GIT_CONFIG_*` environment, set each turn by `inject_git_credentials_into_sandbox`, which also registers a refresher the driver asks before every command so the capability is renewed once less than twenty minutes of its hour remain) at the API's `/v1/git/` routes, which stream git's smart-HTTP protocol to GitHub with a credential resolved on the platform. Reads only. `WorkspaceSpec.platform_endpoints` carries the gateway's `host:port` so the egress proxy (Docker) lets it through; the Kubernetes driver adds a rule for the API pods (`PlatformPeer`, from `ROCKET_PLATFORM_*`). `clone_repository` makes blobless partial clones with all remote branches (`--filter=blob:none --no-tags`) and heals single-branch clones on refresh.
* **Persistent language caches.** To accelerate build/test cycles and survive sandbox pod restarts or hibernations, language cache directories (`GOMODCACHE`, `GOCACHE`, `UV_CACHE_DIR`, `PIP_CACHE_DIR`, `PNPM_HOME`, `CARGO_HOME`) are mapped to `/workspace/.rocket/cache/` via `DEFAULT_SANDBOX_CACHE_ENV` and `Dockerfile.sandbox`. A global git ignore excludes `.rocket/` to keep workspace repositories pristine.
* **Publishing** (`git_engine/publish.py`, `host_repo.py`): the sandbox computes the base and the new commits and makes `git bundle create HEAD ^<base>`; the platform reads it (`sandbox_driver.blobs.read_bytes`), fetches the base commit shallow and blobless into a temporary bare repository, imports the bundle, signs (`gpg_key`) or replays through GitHub's API (`github_app`), pushes, and moves the sandbox's branch onto the published commits when their hashes changed; `PublishResult.rewritten` lists each local commit's replacement, which `git_push` reports to the agent. Under the `co_authored` policy the member's `Co-authored-by` trailer is added to every commit GitHub re-creates (`PublishSpec.co_authors`), whatever made it.
* **Catalogue.** Each organization has a list of sandboxes (name, image, description, capability tags, one default) in `sandbox_catalogue`. A session starts in the entry chosen by name (`SandboxCatalogue.chosen`): the session's own (`metadata.sandbox_id`, from its creator), else its agent's `sandbox_id` when the session names no image either; otherwise the entry matching its image, else the default. Provisioning and the turn's capability check use the same rule; capabilities (e.g. `browser`) decide which optional tools exist for it.
* **Background processes.** `process_start/list/output/wait/stop` run dev servers and watchers in their own process group inside the sandbox (state files under `/tmp/rocket/proc/<id>/`, no daemon). The control plane mirrors them in `sandbox_processes` (`ProcessTracker`), announces `process_started`/`process_exited`, tells the agent at its next turn what exited while it was away, and holds the sandbox awake (`hold_awake(session_id, seconds, reason="process")`) while one runs. Turns also maintain a heartbeat lease (`reason="turn"`), preventing pod hibernation during long turn reasoning or tool executions. In multi-replica deployments, the sandbox reaper runs under leader election (`LeaderElection("sandbox-reaper")`) and validates turn state against PostgreSQL `turn_traces`.
* **Preview.** A minted, port-scoped token serves an app running in the sandbox through `/v1/preview/<token>/…` with a `sandbox` CSP, embedded in an iframe without `allow-same-origin`.
* **Terminal.** An interactive PTY over a WebSocket, gated like a write to the session and audited on open and close.

## 7. Models, configuration, integrations

**LLM gateway.** `LiteLLMGateway.chat_stream` is the single choke point for every model call (the loop, subagents, titles, summaries, follow-ups). Before the call it checks budgets (`BudgetService`, month-to-date from the persisted ledger) and resolves the key (member → organization → platform per `budgets.byok_policy`); after it, it writes one `usage_events` row with prompt, completion, cache-read, and cache-creation tokens and the call's cost: the amount the provider billed when it reports one (OpenRouter usage accounting, `usage.cost`), else LiteLLM's price for the model (also under its name without the `openrouter/` prefix), else the family estimate (`pricing.py`). The same figure travels on the final `StreamChunk.cost_usd`, so the turn telemetry and subagent costs match the ledger. Sticky session routing binds `user` and `prompt_cache_key` to the session id, and `models.provider_preferences` pins an OpenRouter model's providers (a request served elsewhere starts with nothing cached). Generation parameters (output token ceilings up to 64,000 for reasoning models, medium reasoning effort defaults, thinking budgets) are resolved via `ModelCatalogue` (`api/services/model_catalogue.py`) before dispatch. Retries and fallbacks are delegated to LiteLLM (`num_retries`, `fallbacks`) and never retried after tokens have streamed. Prompt caching marks only the stable prefix and tool schemas, preserving serialization order across tool loads. Auxiliary calls use JSON-schema constrained output with one repair retry (`structured.py`). Model choice is decided above the gateway (routing settings). It asks for the usage block where the provider sends it only on request (`stream_options.include_usage`, when `litellm.get_supported_openai_params` lists it); without one, `llm_gateway.tokens.request_tokens` estimates the request (schemas, tool-call arguments, reasoning, images), the same count the context manager uses.

**Settings (`config-engine`).** A typed registry of domains (`general`, `models`, `budgets`, `routing`, `sandboxes`, `github`, `mcp`, `slack`, `governance`, `memory`, `user_preferences`); each key declares kind, default, scope (`org`, `user`, `both`), bounds and the file that consumes it (a test fails if the consumer does not read the key). Resolution is system default → organization value → member override, and an administrator can *lock* a member-overridable key. Writes are validated and rejected, never silently dropped. `effective_settings` returns a `DeclaredSettings` mapping that refuses a key the registry does not declare (`ROCKET_STRICT_SETTINGS=1`, set by the test suite, raises; production logs it once), so a feature gated on an undeclared key cannot ship silently; the AST test only covers the files and variable names it knows. A spec may carry a `label` (when the capitalised key would mislead) and `deprecated=True` (hidden in forms unless a value is stored, flagged in the reference). `doc/administer/settings-reference.md` is generated from the registry. Every key must have a behaviour test marked `@pytest.mark.setting("domain.key")` (enforced by `tests/unit/test_every_setting_is_wired.py`); a member preference must default to empty when it competes with an organization or platform default, otherwise the default counts as the member's choice and always wins.

**MCP.** Organization- and member-scoped servers (command/stdio for administrators only, HTTP/SSE/streamable-HTTP remote), secrets encrypted at rest, OAuth discovery and client registration through the MCP SDK, optional per-member authorisation, tools attached per turn. Presets for common servers are static data in the web app (`settings/mcp/presets.ts`) that only prefill the registration form.

**Command (stdio) servers and the MCP runner.** A command is an arbitrary program, so it runs neither in the API process nor in an agent sandbox but in the `mcp-runner` pod (`packages/mcp-runner`, optional, `MCP_RUNNER_URL`/`MCP_RUNNER_TOKEN`; without it stdio servers are unavailable and the UI says so via `GET /v1/mcp/runner`). One WebSocket (`/v1/stdio`, bearer-token authenticated) carries one server process: the first frame states the command, the environment, the organization and an optional install script; the runner builds a clean environment (never its own variables), starts the process in its own process group and relays newline-delimited JSON-RPC; closing the socket (the end of the turn, `McpToolProvider.aclose`) or `MCP_RUNNER_MAX_LIFETIME_SECONDS` kills the group. Capacity is bounded in total and per organization. There is deliberately no warm pool: an MCP server serves one client session and many reject a second `initialize`, so concurrent turns get one process each and nothing runs between turns; package caches (`/cache`) are what make starts cheap. An install script (`tools.py`) runs once per organization and script hash into `/cache/tools/<org>/<hash>`, without the server's variables, and that directory leads the server's `PATH`. Per-member values for overridable variables live encrypted in `mcp_member_tokens` under the key `env` (`mcp_member_env.py`); `_rows_with_member_env` merges them into a member-specific copy of the row for that member's turn and drops the server when a required value is missing. The probe/test path (`mcp_engine._probe_command`) uses the same runner, so a server is checked exactly as it will run.

**Sharing.** `routers/sharing.py` manages who can open a session: `is_shared` (organization-wide) and `collaborators` (user ids resolved from emails against the organization's users) on the record, plus an optional public link kept in `metadata.public_link` (`{id, url, expires_at}`). The link's token (`auth/share_token.py`, HS256, `typ=share`) names the session and the link id; revoking or replacing the link changes the stored id, so every older token fails verification. `GET /v1/shared/{token}` is exempt from the identity gate, re-checks `general.public_session_links`, and returns only user/assistant text. Writes use `mutate_session`.

**Tool calls written as text.** A model may put its native call syntax in the message text instead of a structured call (`agent_core/leaked_calls.py`). `_stream_model_step` hides it from the live stream (`LeakFilter`), and `_react_step` treats a reply with such markup and no real call as a failed step: it is left out of the conversation, a system notice asks for a proper call (`MAX_LEAK_RETRIES`), and after that the turn ends with a plain explanation. Add a marker there when a new model family does the same.

**Git.** `GitEngine` formats commits with `Co-authored-by` trailers, signs (GPG or GitHub App), opens pull requests, and verifies GitHub webhooks (HMAC; unsigned only if explicitly allowed). Webhook triggers (`issues.labeled` with the trigger label, addressed or labelled `issue_comment.created`, `pull_request`) are accepted only from repository insiders and an optional repository allowlist. Credentials are resolved per session (`resolve_session_git_credentials`: the App's read-only installation token when it can read the repository, else the member's linked account, else the deployment token) and injected into the sandbox; the member's own token stays host-side (`GitCredentialBundle.user_token`). **Publishing** is `GitEngine.publish_branch` (`git_engine/publish.py`), reached by the `git_push` and `git_open_pr` tools with a `PublishSpec` built from the member's *effective* policy (`effective_signing_policy`): `github_app` replays new commits through GraphQL `createCommitOnBranch` so GitHub signs them, `gpg_key` pushes commits the sandbox signed with the member's imported key (`git_signing.py`, validated by GnuPG; key injected per turn in a memory-backed keyring), `none` pushes as they are. The commit identity (`github_identity.commit_identity`) is the git panel override, else the GitHub login and primary or noreply e-mail. **Following pull requests:** `github_watches` (RLS-scoped) records which session follows which pull request or branch (created by `github_watch` or automatically after `git_open_pr`). `GitEngine.parse_repo_event` turns check-suite, review, comment and close events into `RepoEvent`s; `deliver_repo_event` fans one out to the live (not archived) sessions of the installation's organization as a `github_event`, then either starts a turn (`start_turn_on_session`, only for trusted authors, an idle session and under the per-watch wake cap) or keeps it for the next turn's dynamic prompt suffix.

**Memory, knowledge, skills.** Long-term memory (`remember`/`recall`, injected only into the volatile prompt suffix), pgvector knowledge bases, prompt skills and agent personas, all organization- or member-scoped under RLS.

**Missions** are scheduled sessions claimed atomically (`claim_due`) and run on a leader-elected scheduler; a run can report to a Slack channel.

## 8. Slack (`packages/slack-assistant`)

`SlackAssistant` is assembled from mixins that share the state declared in `state.py`: `toolset` (Slack tools and policy; `directory` adds the read-only people, user group, channel member and permalink tools, with `_readable_channel`: the current conversation, an allowlisted channel or a public one), `gates` (approval and question buttons, durable ownership), `admission` (rate limits, quotas, organization policy), `routing` (message classifier, sticky thread routes, private mode acknowledgement, ephemeral summary and sharing), `turn_stream` (run a turn and render events), `entrypoints` (the bot's slash command, the "Ask Rocket" shortcut, App Home, mission reports). `bot.py`, `stream.py`, `artifacts.py`, `health.py`, `block_kit.py` are plain helpers. Behaviour worth knowing:

* **Several bots:** An organization can run multiple bots, each representing an independent Slack app with its own `@handle`, sealed tokens (`slack_bots` table), policy overrides, and target agent or router. Each bot runs under per-bot leader election (advisory lock `slack:<bot_id>`).
* **Response modes:** `thread` (answers in thread with live progress) vs `private` (marks the request with a reaction, sends the requester an ephemeral link, runs in a private session, sends an ephemeral summary on completion, with a **Share in thread** button for voluntary sharing). With the bot's `private_dm_updates`, the turn's `say` is `_direct_say` instead: questions, approvals, errors and the result go to the requester's DMs with a link to the thread, and gate buttons carry their session in their block id (`SESSION_BLOCK_PREFIX`), since no thread names it in a DM; `_may_answer` still checks the clicker against the session's requester.
* **Blocked tools:** `SLACK_BLOCKED_TOOLS` (`DEFAULT_BLOCKED_TOOLS`) is the turn's `denied_tools` unless the turn runs as a linked member (`_Admitted.runs_as_member`: their DM or private request), where they keep their web-app tools unless `slack.restrict_linked_members` is on (`_denied_tools`).
* **Bot manager** (`api/bootstrap/slack.py`, `SlackBotManager`): lists every organization's enabled bots on the schema-owner connection (a cross-tenant read, like the mission claimer) and runs one `SlackAssistant` per bot. `sync()` starts new bots, restarts changed ones (a hash of the record and tokens) and stops removed ones; the replica that saves a bot syncs at once, the others every 30 seconds. Sessions are `slack_<bot key>_<channel>_<thread>`, and a private request's adds `_<requester>`.
* **Router** (`api/services/slack_routing.py`): runs after admission and before any session exists, so a dismissed message creates nothing. The classifier model is resolved through the organization's model policy and the call runs under a `ModelScope` for the bot's organization, so it uses the organization's keys, caps and usage ledger. Structured output (`generate_structured`) by default; OpenRouter System One models (`services/systemone.py`) are called directly, so that path checks the caps and books the usage itself. Every decision is recorded in `slack_route_decisions` (RLS).
* One reply per request, streamed with Slack's agent streaming API (`stream.TurnStream`: `chat.startStream` on the first tool call, a `task_update` chunk per tool call, `chat.stopStream` with the answer and its footer); a turn without tools, or a workspace that refuses streaming, gets a plain reply. Long answers and diffs go out as files. Turns are stopped with the bot's slash command (`/<command> stop`), which only stops the caller's own turns.
* Slack does not namespace slash commands, so each bot has its own (`bot.command_for(handle)`, also in its manifest) and still answers the legacy `/rocket`.
* A thread's pending question survives restarts: the requester is stored on the session (`slack_turn_requester`) and a question whose turn died is answered from its stored copy.
* Socket Mode runs on leader replicas (advisory-lock election per bot); event redeliveries are dropped; a watchdog reconnects silent sockets.
* The Slack tools are registered once on the shared tool registry; each call runs on the live assistant of the bot whose session is executing (`toolset._LIVE_BOTS`, keyed by the bot's session key), so it uses that bot's client, policy and conversations, and a stopped bot's sessions are told Slack is not connected.
* The platform calls back into the assistant only through the callables passed at construction (`api/bootstrap/slack.py`), so the package never imports the API.

## 9. The web cockpit (`apps/web`)

Next.js 15 App Router, React 19, Tailwind, lucide icons, Zustand. The client store is split into slices under `lib/store/` (sessions, agents, stream, composer, layout). `lib/websocket.ts` + `lib/sync-plan.ts` + `lib/session-cursor.ts` implement the resume/sync rules of §5. Shared form primitives (`components/ui/Field.tsx`) tie every label to its control; pages share one top bar. Monaco renders diffs, xterm renders logs and the terminal (the store keeps the latest ~300,000 characters of agent output; `terminalBase`/`terminalEpoch` tell the view what was trimmed or reset). Components subscribe to the store through `useShallow` selectors, and entries derived from an event are named by its `seq` so a replay lands on the entry it made the first time. **Settings pages** register every `SchemaSettingsForm` with one `SettingsSaveProvider` (`components/settings/SettingsSave.tsx`): forms report their change count and the sticky bar saves or discards them all; `advanced` and `unit` come from the registry through `/v1/settings-schema`, and `SettingsSearch` finds pages and keys from the same schema. **Conversation status:** `turns/attention.py` keeps `awaiting_input` and `last_turn_status` in session metadata (set by the event handlers when a gate opens and by turn cleanup when it ends) and publishes them in `session_updated`; the sidebar and header read them through `lib/session-groups.ts`. The inspector's tab, auto-open and terminal state live in the layout slice; only a person's call to `setIsRightPanelOpen` records a preference (kept in `localStorage`), and `autoOpenInspector` never opens a panel the person closed. **Waits and pull requests:** a `wait_started` event becomes one flight-log entry carrying a `wait` record that `wait_completed` settles in place by `wait_id` (`WaitCard`); `github_event` entries carry a `githubEvent` the card shows while it waits. `lib/pull-requests.ts` reads the pull requests a session handled from the results of `git_open_pr`, `github_pull_request` and `git_push`, which the turn summary and the wait card's **Open PR** link share. The **Changes** tab (`ChangesPanel`) reads `GET /v1/sessions/{id}/changes` (`services/workspace_changes.py`: git in the running sandbox against the latest `-turn` checkpoint or the merge base with the default branch; whole files through `/changes/file`; `POST /changes/revert` restores one file) and reads again when a `file_diff` event arrives; the events only serve as a fallback while the sandbox cannot be read. Artifacts are rendered by type (`ArtifactBody`: Markdown, Mermaid drawn with `securityLevel: strict`, HTML in a `sandbox=""` frame, JSON, diff) with a version menu. Playwright (`e2e/`) runs against the in-memory API and, in CI, against a migrated PostgreSQL with forced RLS; `e2e/docs/screenshots.spec.ts` regenerates the documentation screenshots.

## 10. Operations

* **Probes and metrics:** `/health` (liveness, no dependencies), `/v1/ready` (database ping, 503 while draining), `/metrics` (Prometheus text), `POST /v1/drain` (the Helm `preStop` hook). Shutdown sets `draining`, stops background tasks, closes the bus, the sandbox warm pool and the connection pool, in that order.
* **Backpressure:** a global concurrency gate bounds concurrent turns; a bounded registry of per-session locks gives one writer per session.
* **Replicas:** `ROCKET_EVENT_BUS=postgres` turns on the shared bus, cluster session locks, leader election (Slack socket, mission scheduler) and turn-lease recovery. Schema upgrades run at container start (`alembic upgrade head`); the API refuses to start against a schema that is behind.
* **Governance jobs:** a retention sweeper, turn-lease heartbeats and a remote-MCP refresh run on the schema-owner connection because they must see every tenant.
* **Packaging:** multi-stage Dockerfiles in `deploy/docker/`, Compose for evaluation and single-node production, the Helm chart in `deploy/helm/platform` (every new environment variable, secret, mount or route must be added there).
