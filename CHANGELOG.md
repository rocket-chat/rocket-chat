## [0.3.1] - 2026-10-16

### Added
- `slack-assistant`, `api`, `web`: **Several Slack bots per organization, with response modes and message routing.** Each bot is its own Slack app (`@handle`), added in **Settings → Slack** with its tokens (stored encrypted, shown as fingerprints), and answers with its own agent or a router. The cockpit generates the Slack app manifest and checks the tokens with `auth.test`; the first bot binds its workspace to the organization.
  - **Response modes:** `thread` answers in the thread as before; `private` marks the request with a reaction and works in a session only the requester sees, sending them an ephemeral link and summary with a **Share in thread** button (optionally also a direct message). A channel can override the mode.
  - **Routing:** a router classifies each new request to a route (description, examples, agent, response mode) or dismisses it before any session exists; it falls back below a minimum confidence, keeps a thread on its route, and logs every decision (**Activity** tab, **Try it** box). Classifications are billed to the organization like any model call.
  - Bots can also listen to chosen channels without a mention, and can decline direct messages.
  - Migration `029_slack_bots`: tables `slack_bots` and `slack_route_decisions` with forced row-level security.
- `agent-core`, `api`, `web`: **Tools can be loaded on demand.** Each allowed tool is always loaded, loaded on demand or not allowed. A tool loaded on demand is listed by name, grouped by server, in the cacheable part of the prompt; the agent loads it with the new `load_tools` tool (or by calling it) and it stays loaded for the session. The organization chooses the default (`general.tool_loading`: `auto`, `all` or `on_demand`, and `general.tool_loading_threshold`); `auto` loads the MCP servers' tools on demand once an agent has more than the threshold (60). An agent can choose its own mode and pin tools or patterns as always loaded. For an agent with three MCP servers this cuts each step from about 200 tool definitions to the platform's own plus the pinned ones.

### Changed
- `slack-assistant`, `api`: `SLACK_TEAM_ID`, `SLACK_DEFAULT_ORG_ID`, `SLACK_DM_POLICY`, `SLACK_OUTBOUND_CHANNELS`, `SLACK_ALLOWED_TOOLS` and `SLACK_WEB_BASE_URL` are deprecated in favour of the workspace binding and the organization's `slack` settings.
- `api`, `helm`: **`SLACK_BOT_TOKEN` and `SLACK_APP_TOKEN` are ignored** (start-up warns while they are set), and the Helm values `backend.slack.botToken`, `appToken` and `existingSecret*` are gone. Add the Slack app as a bot in **Settings → Slack**; its threads start new sessions.

### Fixed
- `agent-core`: **A turn starts its sandbox only for work in it.** The turn checkpoint taken before the first change started the sandbox for any call that was not a read, so a Slack reply, a GitHub action, an MCP tool or `load_tools` booted a sandbox. Only edits, sandbox commands and git changes are checkpointed now, and `load_tools` is a read (no approval).
- `slack-assistant`: **Slack tools act for the bot that owns the session.** They were bound to the first bot started in the process, so after a bot was edited (and restarted), or with a second bot, they ran on a stopped bot that did not know the conversation, and refused to post in it. The agent is also told that the platform delivers its answer, so it no longer replies through `slack_send_message`.
- `web`: **Settings → Slack shows bots to administrators only.** Members see that bots are managed by administrators instead of an empty list and a **New bot** button; the outdated "Imported from the environment" banner is gone.
- `web`: **MCP tools picked one by one in the agent editor now reach the agent.** The editor saved them as `mcp:<server id>:<tool>` while the agent's tools are named `mcp__<server>__<tool>`, so an agent restricted to selected MCP tools received none of them. Re-select them once to save them under the right name.
- `api`, `web`: **Mapping a GitHub App installation works when the App asks users to authorize during installation.** With that GitHub setting, GitHub ignores the Setup URL and returns the administrator to the OAuth callback with the install link's state. The callback rejected it as an invalid sign-in state, so the installation was never mapped. It is now handed to the installation mapping, with the same checks. **Settings > GitHub** says whether the installation was mapped, and why not. The GitHub guide now gives the exact App settings for both jobs with one Callback URL. GitHub sends the administrator back the moment it creates an installation, before its API returns it: the check now asks again briefly instead of refusing, and every refusal is logged with its reason. The callback now judges the administrator by their current roles, like every other request. Before, it used the roles frozen in the session cookie at sign-in, so a member who became administrator after signing in was refused ("This install link was not issued to you"). The install link is created when it is clicked (`/v1/admin/github/install`), so it no longer expires while the settings page stays open, and an expired link is reported as expired instead of as `InvalidOAuthState`.

## [0.3.0] - 2026-10-15

### Added
- `slack-assistant`: **The agent can look up Slack teams and people.** New tools: `slack_list_user_groups` and `slack_get_user_group_members` (user groups such as `@backend`, with their members and how to mention them), `slack_get_user` (name, title, timezone, status and groups, never the e-mail), `slack_list_channel_members` and `slack_get_permalink`. `slack_read_thread` and `slack_read_channel_history` can now read another public or allowlisted conversation. `slack_resolve_user` searches the whole workspace and returns the closest candidates for a partial name. Slack reads are classified as reads (no approval, allowed in *Plan* mode); sending messages, DMs and reactions counts as publishing. The Slack app needs the `usergroups:read` scope for user groups.
- `agent-core`: **One working folder for every tool.** Relative paths given to the file tools now resolve inside the session's active repository, the folder `bash_exec` and the git tools already use, and results show the absolute path. A path that misses says how to reach another folder. The new `set_active_repository` tool switches the active repository for the rest of the session.
- `agent-core`, `api`: **The agent works on GitHub without `gh`.** The sandbox holds no GitHub credential, so it has no working `gh` CLI. Platform-side tools cover what `gh` was used for. `github_pull_request` reads a pull request's files, paged diff, checks and review threads, and edits, reviews, comments on, replies to and resolves threads, closes, reopens and merges it. `github_actions` lists runs, shows a run's failed steps, reads the end of a job's log, and re-runs, cancels or starts workflows. `github_releases` and `github_search` cover releases and search. `github_issues` can now create, comment on, edit, close and reopen issues. `github_api` makes any other REST or GraphQL call, and refuses secrets, keys, webhooks, installations, access, protection and administration. Changes use the member's account or the organization's App installation for that repository, following `pr_creation`; the App acts only on the repositories `app_token_target_repositories` allows. Each result says who acted. Reads need no approval; changes are publishes; merging and `DELETE` always ask except in *Bypass*. Notices about CI failures and reviews on a followed pull request name the tool that answers them.
- `git`, `api`, `web`: **Verified commits.** `commit_signing_mode` now does what it says. `github_app` (default): the agent publishes with the new **`git_push`** tool (and `git_open_pr`, which publishes first), which re-creates the branch's new commits through GitHub's GraphQL `createCommitOnBranch` so GitHub signs them (verified, made by the GitHub App; needs the App's *Contents: Read & write*). `gpg_key`: a member imports a GPG private key under **Settings → Git & version control → Commit signing** (validated by GnuPG, stored encrypted, public key shown for GitHub) and turns on the new `commit_as_me` setting to commit as themselves, signed with it; everyone else gets the `github_app` behaviour. `none`: unsigned. Signing is transparent: it applies to `git_commit` and to a plain `git commit` in the shell. `GnuPG` is added to the backend and sandbox images.
- `git`, `api`: **The agent can no longer push on its own.** A raw `git push` is refused by a hook that points at `git_push`, and where the GitHub App can read the repository the sandbox's token is read-only and the member's own token stays on the platform, so write credentials never enter the sandbox. Where the App cannot read a repository the member's token is still given to the sandbox (it cannot be narrowed) and only the hook and the instructions apply. Merge commits, symbolic links and submodules cannot be published as GitHub-signed commits (the tool says which); a new executable file loses its executable bit (reported).
- `web`, `api`: **every MCP server can be edited**, remote (HTTP, SSE, WebSocket; API key, custom headers, OAuth) as well as command servers, organization-wide by administrators and personal by their owner. The server list now returns the non-secret connection settings (`header_name`, `header_prefix`, `oauth_token_url`, `oauth_client_id`, `oauth_scopes`, `oauth_authorization_url`); secrets stay write-only and are kept unless replaced. Moving a remote server to another address or OAuth client disconnects its accounts. `POST /v1/mcp/servers/validate` accepts the server's `id` so *Test* works without retyping secrets, under the same access rules as saving.
- `web`, `api`: administrators can **edit an organization command server** (pencil on its card): command, install script, variables, member overrides and guidance. Secrets are never sent back to the page; sending `null` for a header keeps its stored value and an empty string clears it (kept only if the caller may modify the server, and for a remote server only while its address is unchanged). Members' own values survive the edit.
- `web`, `api`: administrators can edit the built-in agents (for example **General Software Engineer**) for the whole organization, and **Reset to default** restores the shipped definition. The edit is stored as an organization row that replaces the built-in (migration 027), is applied to every turn and never leaks to another organization; members keep saving their own copy. `DELETE /v1/agents/{built-in id}` resets it.
- `web`, `api`: a custom agent can set its own "Max steps per turn" in its settings form, from 1 up to the organization's `max_turns`; empty inherits the organization's limit. A higher value is refused with the ceiling in the message, an agent is also capped at run time if the organization later lowers its limit, and `GET /v1/agents/limits` reports the ceiling. The persona API now accepts up to 200 (it stopped at 100 before).
- `orchestrator`: `search_tools` lists the tools available in the session, optionally filtered by keyword, so an agent can look a tool up instead of guessing its name.

### Changed
- `web`/`doc`: Refreshed the Rocket Chat logo and favicons from the current design across every copy in the repo (`apps/web/public`, the Next.js convention icons in `apps/web/src/app`, and `doc/assets`), and raised the app-wide type scale (`text-xs`…`text-3xl`) for readability.
- `slack-assistant`: **No leftover "Done" message in Slack threads.** The live progress message, with its recent steps and Stop button, is now removed when a turn finishes, after the answer is posted. The answer ends with one line: the session link and what the turn did ("Done in 41s · Edited 2 files · Ran 3 commands"). A stopped or failed turn keeps the message, saying why; a workspace that refuses the deletion gets the old "Done" message.
  - the workspace: repositories in `/workspace/<name>`, the active repository as the default for tools, shells and relative paths, a fresh shell per command, clamped output and reading by range;
  - how to edit (`file_edit`/`apply_patch`, `file_write` for new files) and verify;
  - the git workflow: never commit to the default branch, publish with `git_push`/`git_open_pr`, the organization's signing mode, and the `github_*` tools in place of `gh`.

  The default agent's prompt is now one model-agnostic text: a versatile senior software engineer. The built-in security agent no longer pins a provider-specific model; it uses the member's or organization's choice and gets the code-search tools. The repository's own instructions are remembered on the session, so a turn that finds the sandbox asleep keeps the same cacheable prompt.
- `agent-core`, `web`: **Subagents can do their job.** The researcher and security auditor can search the code (`grep_search`, `glob_files`, `list_dir`, `code_search`), and the QA verifier can run `run_tests`. Built-in roles get 12 steps instead of 4, and an administrator can set 1 to 60 per role. A subagent is told which repository it is working in and how the sandbox behaves. Its tool calls share the session's concurrency, time budget and file locks. When its steps run out mid-work it still writes a report. **Settings → Subagents** shows the same defaults as the platform.
- `orchestrator`, `llm-gateway`: **the conversation is now served from the provider's prompt cache.** Each request is laid out as the stable prompt, then the history, then the turn's volatile context (routing notice, background processes, GitHub activity, recalled memories), which used to sit before the history and so made the history uncacheable from one turn to the next. Providers with explicit cache markers (Anthropic-style, also through OpenRouter, Bedrock or Vertex) get a rolling breakpoint on the last message, so every step of a turn reads the previous step's history from the cache instead of paying for it again; providers that cache prefixes automatically benefit from the stable order. MCP tools are listed in a stable order. The turn trace reports a `cache_hit_ratio`.
- `ci`: the manual **Dev images** workflow also builds and pushes the `sandbox` image (the agent workspace), so a branch's sandbox changes can be tried with the other `:dev` images.
- `api`: **commits made as the member are attributed to their GitHub username and primary e-mail** (falling back to the account's `id+login@users.noreply.github.com` address) instead of their display name; the git panel shows the identity in use and the member can still override name or e-mail. Without a linked account the profile name is used as before.
- `web`: settings pages share one quieter look: interface text, labels and buttons are set in the sans typeface (monospace stays for code and prompts), buttons use the shared button, headings use the shared page header, and the scope badges and divider pill are gone.
- `web`: each settings page has a single "add" action per section (the duplicate "Register MCP server" and "New agent persona" header buttons are removed; organization actions say "org").

### Fixed
- `web`: `RocketChatIcon` now renders the shared `/favicon.svg` asset instead of a second, hand-coded copy of the artwork, so the two can no longer drift out of sync; the auth middleware's static-asset allowlist was missing the `public/` logo files, so it now also exempts them.
- `slack-assistant`, `agent-core`: **MCP tools (SigNoz, Atlassian, Grafana…) were missing on Slack.** With `allowed_tools` set to `*`, Slack built a list of the tools registered before the turn. MCP tools are attached only when the turn starts, so none of them reached the model, and the agent said it had no SigNoz access. `*` now stays unrestricted, and Slack's blocked tools are enforced separately (`TurnOverlay.denied_tools`): they are neither offered nor run.
- `api`: **Pairing a Slack account no longer claims the database is missing.** When the signed-in member's row is not in their organization, `/v1/slack/pair` now answers 409 and says so. Sign-in now logs an error when a member's row is in a different organization from the one sign-in assigns (for example after `ROCKET_SSO_ORG_MODE` changed), instead of a quiet warning.
- `agent-core`: **No `<tool_calls>` fragments in answers.** When a model writes its tool calls as plain `<tool_calls>`/`<invoke>` tags, the opening tag is now recognised as markup too. Before, it passed the stream filter and every discarded attempt left one `<tool_calls>` line in front of the "wrote a tool call as text" message.
- `slack-assistant`, `api`: **Slack turns got no tools when the agent allows every tool.** The Slack tool selection was intersected with the agent's whitelist literally. For the built-in engineer agent (`["*"]`) that left nothing, so the model wrote its calls as text and no tool ever ran. The runner now passes an unrestricted agent as `None`, as the `TurnOverlay.tool_scope` contract says, and Slack admission treats `*` as unrestricted too.
- `slack-assistant`, `api`: **Slack sessions of unlinked users and shared threads were handed to a development identity.** Production never creates unknown users, so saving a session owned by a raw Slack id (or by `slack_global`) failed. The turn runner then created the session as `dev_user` in `default_org`, titled with the raw `[Speaker: …]` prompt. Such sessions now belong to guest members the Slack bridge creates (`slack:<team>:<user>`, `slack:<team>`, read-only, no sign-in), and pairing moves a guest's sessions to the member. The runner no longer invents sessions outside development. Slack sessions start with a placeholder title the AI titler replaces, and titles ignore the speaker attribution.
- `llm-gateway`, `agent-core`: **Usage is reported accurately.** OpenAI-compatible providers (OpenAI, Azure, OpenRouter, DeepSeek, vLLM, Groq, ...) only stream token usage on request, so the gateway now asks for it wherever LiteLLM says the model supports it. Usage that arrives on an ordinary content chunk is kept. When a provider reports nothing, the estimate counts the whole request: tool schemas, tool-call arguments, reasoning and images. One counter (`llm_gateway.tokens`) serves the ledger, the turn loop, subagents and context compaction. Before, a turn that wrote a large file through a tool call was billed almost nothing.
- `api`: **Changing a session no longer erases what a running turn just recorded.** Renaming a session, changing its permission mode or agent, sharing it (over HTTP or the WebSocket), and resuming it from a GitHub webhook used to write the whole record back as it was read. A turn's answer or its active repository stored in between could vanish on PostgreSQL. These now change only their own fields under the row lock. A webhook follow-up also pulls in the session's active repository instead of `/workspace`.
- `orchestrator`, `web`: **every file change appears in the changes panel, once.** Only `file_edit` and `apply_diff_file` reported diffs, each of them twice; a file created with `file_write`, a patch from `apply_patch` and anything a shell command changed (`sed -i`, a formatter, a generator) never showed. Each tool now reports its change exactly once, and the files a `bash_exec` changes in a repository are reported as diffs against the last commit.
- `sandboxes`: **Kubernetes: a pod is no longer marked evictable while it is still working.** Eviction protection was switched on and off around each command, so with two commands running at once the first to finish let the autoscaler evict the pod under the second, and a dev server started with `process_start` was never protected. The driver now counts running commands per session and keeps the pod protected while any runs or background processes hold it, writing the annotations only when that changes (two API calls per command before).
- `sandboxes`: **Docker: editing a file keeps its mode and owner.** Files written by the agent were recreated root-owned with mode 0644: an edited script lost its executable bit, and in a non-root sandbox the agent could not change a file it had just written. Existing files keep their mode and owner; new ones belong to the owner of their folder.
- `orchestrator`: **`bash_exec` shows everything the command printed.** A successful command's stderr (warnings, progress, many tools' normal output) was dropped, and a command that timed out lost everything it had printed; both are now in the result, with a pointer to `process_start` for servers and long builds. `glob_files` lists files the way the repository's own tools do (`.gitignore` honoured, `.git`, `node_modules`, virtual environments and build folders skipped) and says when it capped the list. A tool call cut off at the model's output-token limit is no longer run with broken arguments: the model is told to split the work.
- `orchestrator`: **long tool output stays within budget and says what it left out.** Output over 400 lines kept its head and tail but a few very long lines (minified code, a JSON blob) could still flood the context with megabytes; the byte cap now holds whatever the shape, over-long lines are cut, and the marker names the hidden range and how to get it. `file_read` returns numbered lines 400 at a time with the file's length and how to read on (instead of a head and tail with an unknown gap), and `file_edit` accepts a block pasted with those numbers. `web_fetch` reads a page in 20,000-character windows (`start`, `max_chars`) instead of returning up to 100,000 characters at once.
- `llm-gateway`: **a refused provider call is an error, not the assistant's answer.** A bad key or an unknown model came back as the model's own text ("⚠️ LLM Provider Error …"), so it was stored as the reply, could title the session and was billed as a call. It is now an error that ends the turn with an actionable message (fix the key in Settings > Models, or check the model name), shown as an error notice, and a refused call is not billed.
- `orchestrator`, `llm-gateway`: **extended thinking works across a tool loop.** With an agent's thinking budget set, an Anthropic-style model's signed thinking blocks were not sent back with the tool calls they led to, so from the second step the provider refused the request (or LiteLLM silently turned thinking off); `temperature` was also sent although extended thinking only accepts the default. Reasoning is now kept on the step that made the calls and returned the way each provider family requires (thinking blocks for Anthropic-style models, `reasoning_content` within the tool loop for DeepSeek, nothing for others). The text a model writes before its tool calls is kept too.
- `orchestrator`: **compacting a long session keeps what the person asked last.** Compaction anchored the session's first message, so in a long session the current request could be summarised away mid-turn; and "the latest turns" it kept were the last six messages, which could cut a step from its tool results. It now keeps the current request verbatim and the last whole steps, gives the summariser the current goal and the checklist, and lets the summary grow with what it replaces.
- `orchestrator`, `settings`: **long turns no longer run past the model's context window.** The size of a request was estimated from message text only, so tool-call arguments (a large `file_write` or patch), reasoning, images and the tool schemas were not counted and compaction started too late; a provider's "context length exceeded" then failed the turn. The estimate now counts all of it and never goes below what the provider measured for the turn's previous request, an overflow is compacted and retried once, and the new organization setting `models.context_windows` sizes models the platform does not know (a BYOK or self-hosted model). Window sizes now come from the provider library first, with current model families as the fallback.
- `orchestrator`, `web`: **questions and approvals wait as long as it takes.** The 10-minute per-tool timeout also applied to `ask_question`, approvals and the approval inside `apply_diff_file` or a hard `git_revert`, so an answer given later reached nothing; and a waiting call held one of only 8 tool permits shared by every session, so a few sessions waiting for approval stopped everyone's tools. Time spent waiting for a person no longer counts against `ROCKET_TOOL_TIMEOUT_SECONDS` and holds no permit. `ROCKET_TOOL_MAX_CONCURRENCY` now limits **one session's** parallel calls, and the new `ROCKET_TOOL_PROCESS_CONCURRENCY` (default 64) limits the process. Answered questions are forgotten instead of kept in memory, and the cockpit removes a question or approval card when its turn ends.
- `orchestrator`: **a turn that ran out of steps no longer tells every later turn to stop using tools.** The budget notice, the step-limit and error-synthesis instructions, the checklist reminders and the "tool call written as text" notice were stored in the conversation as system messages; providers whose API takes a single system prompt (LiteLLM moves every system message there, for example for Anthropic- and Gemini-style models) turned them into standing rules, so after one exhausted turn the agent was told "Do NOT call any more tools" for the rest of the session. They are now sent at the end of the request they concern, as a reminder, and never stored; the compaction summary is a reminder too. Sessions saved by earlier versions are cleaned when they are next loaded.
- `git`, `orchestrator`: **git, test and build tools act on the cloned repository.** `clone_repository` puts code in `/workspace/<name>`, but `git_status`, `git_diff`, `git_log`, `git_commit`, `git_branch`, `git_checkpoint`, `git_revert`, `run_tests`, `lint`, `typecheck`, `build` and `package_manager` ran in `/workspace`; `git_commit` even ran `git init` there and committed the clone as an embedded repository, which then broke `git_push`. Every one of them now takes an optional `path` and otherwise uses the session's **active repository** (the first one cloned, kept across turns), `/workspace` when it is a repository, or the only repository under it; with several and no choice it names them. `bash_exec` takes a `cwd` and defaults to the active repository. Committing never creates a repository. The automatic checkpoint covers every repository in the workspace, and the checkpoint endpoints report the repository they act on (`repository`). `git_diff` and `git_log` name the file they scope to `file` (was `path`).
- `orchestrator`: **a tool call written as text is no longer shown as the answer.** Some models (DeepSeek's `<｜DSML｜ …>` blocks, `<tool_call>` tags) sometimes write their tool calls into the message when the provider does not parse them: nothing ran and the markup was posted to Slack or the chat as the reply. The markup is now kept off the live stream, discarded from the conversation, and the model is told to make the call properly (up to twice); if it keeps doing it the turn ends with a plain message saying so instead of markup.
- `git`: **`git_push` and `git_open_pr` work on a repository cloned into a subfolder** (where `clone_repository` puts it): they find the repository under `/workspace` (or take a `path`) instead of only looking in `/workspace` itself.
- `git`: **`git_push` works on the shallow, single-branch clones `clone_repository` makes**: it fetches the branches it needs with explicit refspecs and takes the base branch from the clone's own `origin/HEAD`, instead of failing to find `origin/<branch>` after publishing.
- `git`: **publishing no longer fails when the GitHub App has no installation mapped to the organization**: with no App token available, the branch is published with the member's own linked GitHub account (and the result says so); with neither, the error names what to check.
- `api`: editing a command server could lose a secret: the organization's default of a variable members may override was blanked on every save, and probing a variable with no value failed with a decryption error instead of running the server with the variable empty.
- **The share dialog opened off-screen.** It was drawn inside the page header, whose blur made the header the dialog's frame, so it was centred on a 56px strip and cut off at the top. It now opens over the whole window.
- **A late agent-list refresh could wipe what you were typing** on the agents settings page. The form now follows a refreshed list only while it is untouched.
- `web`: the agents page showed the shipped definition of a built-in agent after a reload even when the server held an edited one; the form now follows the refreshed list.
- `orchestrator`: agents now know which skills exist. The system prompt lists the skills the member's agent may load (name and summary), and `execute_skill` is described as loading instruction skills as well as running code ones. Before, nothing named the skills, so an agent could not use one unless the user typed its slash command.
- `orchestrator`: when the identical tool call has failed twice, the third failure carries an explicit "do not send it again, change the arguments" note (the call still runs).
- `api`: `POST /v1/skills` accepts a skill with only a `title` (as the cockpit form and agents send it) instead of answering 422 "name: Field required"; the title becomes the name, and a body with neither is refused with a clear message.
- `orchestrator`: long turns no longer drift without direction. A checklist left untouched for 8 agent steps triggers a reminder (repeated every 8 steps), `update_status` is now a phase indicator rather than a mandatory call before every tool, and the system prompt asks the agent to define "done" up front, batch independent calls into one step, not repeat failed searches, and claim "nearly done" only before the final answer.
- `orchestrator`: an agent that is about to answer while its task checklist still has pending or in-progress tasks is asked, once per turn, to settle the list first (completed, failed, or dropped). The `update_task_checklist` description now states the rules: send the whole list, one task in progress, update as each task finishes, nothing open at the end, empty list clears.
- `web`: the agent/model picker in the composer no longer goes dead while a turn runs or waits for an approval (the button was disabled without looking disabled). It opens, and the choice applies to the next message.
- `orchestrator`: a call to a tool that does not exist now answers "there is no tool named X", suggests the closest real names and points to the new `search_tools` tool, instead of a bare "Tool execution failed". It is refused before the approval gate, so a person is never asked to approve an invented tool.
- `mcp-runner`: a program installed by an install script is found wherever the archive unpacked it (top level, `bin/`, or `<name>_linux_amd64/bin/`, as SigNoz's release does), instead of failing with "not found".

### Security
- `git`, `helm`: **no GitHub credential is shared between organizations any more.** A deployment-wide `GITHUB_TOKEN` (or `GITHUB_PAT`) used to stand in for the GitHub App for every member who had linked nothing, in every organization, and was given to their sandboxes labelled read-only although a personal token cannot be narrowed. It is no longer read: an organization's sandboxes, publishing and pull requests use its own mapped App installation or the member's linked account, and without either only public repositories are reachable. **Upgrade note:** remove `GITHUB_TOKEN` from your environment and the chart's `github.token` / `github.existingSecretTokenKey` (they are ignored); map your GitHub App installation to each organization (Settings > GitHub) or have members link GitHub. The credential modes are now named after what they are (`app`, `member`, `public`; the settings page says how GitHub is read), and the agent is told plainly that its sandbox holds no credential and how clone and publishing work.
- `sandboxes`: **the Kubernetes driver no longer puts a command's environment on its command line.** It was inlined as `export KEY=value` into the exec argv, readable by any process in the pod and recorded in the API server's audit log of exec requests (the GitHub token at the time). It is now sent on the exec's stdin; the interactive terminal reads it from a private file it deletes at once.
- `git`: **branches are published from the platform, and commits are signed there.** `git_push` / `git_open_pr` used to run `git push` inside the sandbox with the write token in its environment, where a hook, a credential helper or a `pushurl` the agent had set could capture or redirect it; and in `gpg_key` mode the member's private key and passphrase sat in the sandbox for the whole turn. Now the sandbox only hands over a bundle of the new commits; the platform imports it into a throwaway repository, signs the commits with the member's key there (`gpg_key`; local hashes change and the sandbox's branch follows), replays them through GitHub's API (`github_app`) or pushes them, with a credential and a key that never enter the sandbox. The `origin` remote is parsed strictly against the GitHub host (an address that merely contains `github.com/owner/repo` is refused). Publishing also works for a repository with no commits yet, replaces a moved-on remote branch with `force_with_lease`, treats a branch deleted on GitHub (after its pull request merged) as new, and no longer creates the remote branch before every check has passed.
- `git`, `sandboxes`, `helm`: **sandboxes hold no GitHub credential any more.** They clone and fetch through the platform's new read-only **git gateway** (`/v1/git/…`): the sandbox's git is pointed at it by per-command environment, with a capability that names one session, lasts an hour and is renewed every turn, and the gateway adds the GitHub App's read token or the member's token on the platform side. Pushing through it is refused. Before, a sandbox received the member's own token (with write access) when no App covered the repository, and the model could read it with `env`. New settings `ROCKET_GIT_GATEWAY_URL` and (Kubernetes) `ROCKET_PLATFORM_NAMESPACE`, `ROCKET_PLATFORM_POD_LABELS`, `ROCKET_PLATFORM_POD_PORT`, all set by the Helm chart; the chart's sandbox NetworkPolicy allows the API pods' port. Docker sandboxes reach the API at `host.docker.internal` (mapped on every engine); restricted ones through a single pinned exception in the egress proxy. Repository setup scripts run without the capability.
- `api`: the GitHub App token given to a sandbox is **always read-only**: whatever `github.app_token_permissions` asks for is lowered to `read` before the token is requested, so an administrator's `write` or `admin` there can no longer give the agent a way to push around `git_push`. Reads such as `actions`, `checks` and `statuses` can still be added.

### Security
- `api`: **Testing a stdio MCP connector ran the administrator's command inside the API process.** The connector "test" launched the configured command on the control plane host - next to the database credentials and the cluster token - so any organization's administrator could execute code there. The control plane no longer launches stdio servers at all: they run in the session's sandbox (see the stdio entry above) and the test explains that, instead of executing anything. **
- `git-engine`: **One organization could obtain a GitHub App token for another's repositories.** The App minted a token for whichever installation GitHub listed first, or for any installation that covered a repository name the caller supplied, so with several organizations on one platform an organization could read (and, for bot pull requests, write to) repositories installed by another. Tokens are now minted only for installations the organization mapped; **upgrade note:** single-organization installs that relied on the old behaviour must map their installation (Settings > GitHub) or set `GITHUB_APP_ALLOW_UNMAPPED_INSTALLATIONS=true`.
- `sandbox-driver`/`deploy`: **Organization egress rules are now enforced on Kubernetes.** `governance.egress_allowlist` and `block_internal_subnets` were computed and carried on the workspace spec but nothing applied them. A restricted sandbox now gets its own NetworkPolicy before its pod starts (DNS plus the allowlisted CIDRs/IPs/resolved hosts, or the internet minus private ranges), the chart's namespace policy no longer applies to restricted pods (policies are additive), and the controller role may manage network policies. The Docker driver still cannot enforce egress and says so. **
- `deploy`: **Safe production defaults.** `docker-compose.prod.yml` was byte-identical to the evaluation compose: default encryption/session/database secrets, PostgreSQL published on the host, no `ENVIRONMENT=production`. It now refuses to render without real secrets, runs the API in production mode, does not publish PostgreSQL, and creates the `rocket_app` role from a secret (the old init SQL hard-coded its password) with least privilege - rows only, no DDL; the Helm bundled PostgreSQL gets the same grants. The Helm sandbox NetworkPolicy now denies all ingress and, by default, egress to private ranges (agent code could reach the database, the API and other tenants' sandboxes). `docker-compose.yml` stays the evaluation stack and gains the developer login its quickstart silently lost when development logins were locked down. **
- `api`: **Generic OpenID Connect through discovery.** Enterprise login was hard-wired to Keycloak's URL scheme, used no nonce or PKCE, did not verify the ID token, and trusted unsigned state. It now finds every endpoint from `/.well-known/openid-configuration` (checked against the configured issuer), uses PKCE (S256) and a nonce, verifies the ID token's signature against the provider's JWKS (with key-rotation refetch), issuer, audience/`azp`, expiry and nonce using `joserfc`/Authlib, refuses unverified emails, and signs the OAuth `state` for every provider (the PKCE verifier and nonce stay in an HttpOnly cookie bound to that state). Bearer-token validation discovers its JWKS from the issuer too, and only ever accepts asymmetric algorithms. Verified against a fixture provider with Azure-style endpoints. **
- `api`: **MCP OAuth hardened.** Any member could start the OAuth flow of an *organization* server and overwrite its shared token, the callback never checked who returned, tokens were stored in plaintext in a field called `encrypted_auth`, client secrets were never sent to token endpoints, and tokens were never refreshed. Now: organization servers are connected by administrators only and personal ones by their owner; the authorization state is bound to the member and organization and must come back from the same authenticated account (single use); tokens are encrypted at rest and refreshed shortly before expiry; token endpoints get the SSRF guard; re-saving a server keeps its connected account. Legacy plaintext tokens keep working and are re-encrypted on the next login. **
- `slack-assistant`/`api`: **Slack account takeover closed.** `/rocket-pair <email>` linked whoever typed an address to that account (including its GitHub token and memories). Pairing is now a one-time code issued ephemerally in Slack and **confirmed from the member's authenticated Rocket session**; e-mail auto-linking is off by default and only matches inside the workspace's own organization (lookups used to cross organizations). **
- `slack-assistant`: **Only the requester can answer an agent's question or approval** in a shared channel (any user could click Approve before); policy-decided gates are not shown to humans. **
- `slack-assistant`: Shared channel threads never use a member's credentials (they were injected for whoever spoke first); the Slack toolset defaults to deny for outbound posting except the invoking conversation, no longer lists direct-message conversations unless the org allows DMs to everyone, and no longer discloses member e-mail addresses. **
- `api`: **Authentication is always enforced.** A single resolver (`api/auth/identity.py`) now establishes identity for HTTP and WebSocket; the `AuthMiddleware` is always installed and anonymous requests get `401`. `X-Tenant-*`/`X-User-Role` headers and the anonymous `dev_user` admin only work with `ROCKET_TRUST_PROXY_HEADERS` / `DEV_AUTH_BYPASS` (never in production). Previously any caller could be an administrator of any organization. **
- `api`: **Fail-closed production mode** (`ENVIRONMENT=production`): startup is refused with default/missing `SESSION_SECRET` or `ENCRYPTION_MASTER_KEY`, or with dev bypass/login enabled; the credential cipher and session signer no longer fall back to public default keys. Helm now requires `auth.sessionSecret` and `backend.encryption.masterKey` (no defaults) and sets `ENVIRONMENT=production`; chart linting uses `deploy/helm/platform/ci/values.yaml`. **
- `api`: **`dev-login` locked down** - disabled unless `DEV_AUTH_BYPASS`/`ROCKET_DEV_LOGIN`; client-supplied roles/org are ignored without the explicit bypass. **
- `api`: **WebSocket authentication and ACL** - cookie/bearer/`?token=` identity, session ownership/sharing/org enforced regardless of OIDC, read-only role cannot steer, only owner/admin can change sharing. **
